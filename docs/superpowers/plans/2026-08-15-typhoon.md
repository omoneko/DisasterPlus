# ④台風 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** バニラの雷雨災害スロット 1 個を土台に、④が経路・天候・落雷・風害・河川氾濫・巨大な回転雲を毎 tick 駆動する**移動する台風**を作る。①②と違い**バニラに原資が無い**ので、④は全体が「新規現象」枠であり、その事実を隠さずに出す。

**Architecture:** ④は「バニラ災害の合成体」ではなく **④が所有する 1 個の論理オブジェクト**である（事実文書 §E-2）。`ThunderStormAI` の災害スロットを 1 つ取り、`m_targetPosition` を毎 sim tick 書き換えて動かす（§E-1）。災害の `SimulationStep` は 256 sim フレームに 1 回しか回らないので、位置・天候・落雷・被害の駆動は全て `IDisasterFeature.OnSimulationTick`（＝ `OnAfterSimulationTick`）から④自身が行う。読み取りは sim スレッド、UI は main スレッドで、①②と同じ snapshot-then-render（単一の素の `lock`）で渡す。被害は `DisasterHelpers.DestroyBuildings/DestroyNetSegments/DestroyStuff` を**一切通さず** `BuildingAI.CollapseBuilding` を直接呼ぶ（§F-1、NDR と無衝突）。雲だけは main スレッドの `Graphics.DrawMesh` で、他のどの要素からも依存されない単独タスクにする。

**Tech Stack:** C# 7.3 / .NET Framework 3.5、Unity 5.6、ColossalFramework UI、xunit / net8.0（Core テスト）、MSBuild。

## Global Constraints

- **.NET Framework 3.5 / C# 7.3**、Unity 5.6。C# 8+ 構文（switch 式、`??=`、範囲演算子、`using` 宣言、null 許容参照型）は**コンパイルエラー**になる。Unity 5.6 以降に追加された API は存在しない
- `Core/` はエンジン非依存。`UnityEngine` 不可、Cities API 不可、`System.Random` 不可、**LINQ 不可**。net35 の MOD と net8.0 の xunit テストプロジェクトの**両方**にコンパイルされる
- net35 に `System.Collections.Concurrent` は無い。共有状態は単一の素の `lock`
- **スレッド境界**: `DisasterManager` / `BuildingManager` / `TerrainManager` / `WeatherManager` / `WaterSimulation` と全ゲームバッファは **sim スレッド**が所有する。`UIComponent` / `InfoManager` / `CameraController` / `Graphics.DrawMesh` は **main スレッド**が所有する。境界を破るとスタックトレースの無い `IndexOutOfRangeException` が後からバニラのコードの中で出る。確立した型は snapshot-then-render（単一の素の `lock`）
- 名前空間は `Game/` が `DisasterPlus.Game`（サブフォルダに関わらず）、`Core/` が `DisasterPlus.Core.*`。**この MOD の `LogChannel` は常に完全修飾する** — `Assembly-CSharp` がグローバル名前空間に同名の型を宣言している
- `Strings` / `Locales/en.txt` / `Locales/ja.txt` のキー集合は常に一致させる（**現在 156**）。追加したら `tools/GenerateLocaleTemplate.ps1` で `en.txt` を再生成する。`Locales/*.txt` は UTF-8 **BOM なし**。**`.ps1` は ASCII のみにする**
- 保存設定は公開契約。**キーは足すだけで、既存のキー番号もビット値も詰め直さない**
- 全セッション状態はレベルアンロードでリセットする。2 つ目の都市がきれいにロードできること
- `Log.Warn` / `Log.Error` はスロットルされない。**毎フレーム・毎 sim tick の経路に置かない。** 1 回だけ出して以後は `Log.Diag` のキー単位スロットルへ落とす
- フレーム → 時間の換算は **`FeatureHost.FramesPerMinute` から出す**。定数を直書きしない
- ビルド: `powershell -ExecutionPolicy Bypass -File build.ps1`、**警告 0**。テスト: `dotnet test tests/DisasterPlus.Core.Tests/DisasterPlus.Core.Tests.csproj`（**現在 297 件緑**）。800 行を超えるファイルを作らない
- **PowerShell の `Get-Content -Raw` → `Set-Content` でファイルを編集しない**（日本語が化ける）。Write/Edit ツールを使う
- コミットは `<type>: <説明>` 形式（feat/fix/docs/test/chore/refactor）。説明は**日本語**
- ブランチは `feature/typhoon`（`456e585` から作る）。**コミットのみ。push もマージもしない**

## ④の表示規約（①②とは違う。全タスク共通）

①はバニラが既に計算していたハザードマップを見せ、②はバニラが既に持っていた決定論的な被害モデルを見せた。**④にはその原資が無い**（設計書 §1.2）。したがって②が確立した `[measured]` / `[Disaster + model]` の**行ごとの二層表示は④には当てはまらない**。全部が同じ出所なら、行ごとの印は情報を持たない。

| | ④の規約 |
|---|---|
| 原則 | **④が出す数値は全て本 MOD のものである。** パネルの見出しで**一度だけ**言う（`Strings.TyphoonModelHeader`） |
| 行ごとの印 | **付けない** |
| 唯一の例外 | `WeatherManager` から読んだ**雨量・雲量**。これは①と同じバニラの実測値なので `Strings.SourceVanilla`（`[measured]`）を付ける |
| `Strings.SourceModel` | **`Game/Typhoon/` と `Game/UI/TyphoonPanelButton.cs` に 1 度も現れてはいけない** |

**機械的に確認できる形にする**（タスク 5 で導入し、以後のタスクは守るだけ）:

1. `UILabel` を作ってよいのは `TyphoonRows.AddLabel` の 1 箇所だけ。公開するのは `AddTitleRow` / `AddSectionHeader` / `AddRow` / `AddRow(height)` / `AddMeasuredRow` の 5 系統

## 出してよい断定の範囲（設計書 §7、全タスク共通）

1. **「あと何分で上陸」は出してよい。** ④が経路を決定論的に持っているので確定値である。①の乱数由来の発生判定とは根拠が違う。**その違いをパネルに書く**（`Strings.TyphoonLandfallNote`）
2. **風速を「m/s」で出さない。** ④の風速相当はゲームの倒壊確率係数であって実在の風速ではない。②が気象庁震度階級を名乗らなかったのと同じ理由。段階（0〜10）と ASCII バーで出す
3. **氾濫が起きなかったとき、その理由を出す。** 対象マップに `TYPE_NATURAL` の水源が無ければ**正常に何も起きない**。①の「なぜハザードマップが空か」・②の「内陸マップに津波は来ない」と同じ扱いにする
4. **プレハブ値が読めないときは何もしない。** 推測した半径・持続時間で台風を動かさない（タスク 2 と 3 が構造で保証する）

## 2 つの乱数生成器（Task 1 で②が定めた規則をそのまま適用する）

> その数字が「この MOD が発明した判断」を決めるなら `DeterministicRandom`。
> 「バニラが引く値と一致しなければならない」なら `VanillaRandomizer`。

**④が引く乱数は全て前者である。** 経路の曲率も、落雷の散布点も、風害の当たり判定も、④が発明した判断であってバニラが引く値ではない。`Core/Earthquake/VanillaRandomizer` は④のコードから**1 度も参照しない**。この規則は両ファイルの doc に既に書いてあるので、④は新しく書かず**守るだけ**である（レビューの grep: `src/DisasterPlus/Core/Typhoon/` と `src/DisasterPlus/Game/Typhoon/` に `VanillaRandomizer` が 0 件）。

### 1.1 経路を「累積」ではなく「閉じた式」にする理由

`position += velocity` の積算にすると、経路が過去の全 tick の呼び出し履歴に依存する。ロード直後・ポーズ・ゲーム速度 1/3/9 倍・診断ダンプの取得タイミングで**同じセーブが違う経路を描く**ようになり、しかもそれをユニットテストで固定できない。

そこで **`CentreAt(seed, elapsedFrames, speed)` を `elapsedFrames` の閉じた関数**にする。曲率 `κ` を種から 1 個引き、進路を円弧にすれば閉形式が存在する:

```
θ(t) = θ0 + κ·t
κ ≠ 0:  X(t) = entryX + (v/κ)·( sin(θ0 + κt) − sin θ0 )
        Z(t) = entryZ + (v/κ)·( cos θ0 − cos(θ0 + κt) )
κ = 0:  X(t) = entryX + v·t·cos θ0
        Z(t) = entryZ + v·t·sin θ0
```

`κ → 0` の極限で下の式に一致する（`(sin(θ0+κt) − sin θ0)/κ → t·cos θ0`）。**この連続性はテストで固定する** —— `κ` の分岐は「小さいけれど 0 ではない」値でだけ壊れる典型的な形なので、目視では絶対に見つからない。

**上陸減衰だけは積算でよい。** これは経路ではなく「これまでどれだけ陸の上に居たか」という履歴そのものであり、`decay` という 1 個の float を④が持ち越す。`DecayAfter` はその 1 ステップぶんの純関数にして、テストできる形に切り出す。

### 1.2 速度をプレハブの `m_activeDuration` から出す理由（**この設計が T2 を先に置く理由でもある**）

`ThunderStormAI.IsStillActive` は `currentFrame - m_activationFrame < m_activeDuration`（§A-1）。つまり**④の台風は `m_activeDuration` より長生きできない**。これを無視して④が好きな速度を選ぶと、台風が都市の真上に居るのにバニラが勝手に `DeactivateDisaster` を呼び、天候が 0 に戻り、④だけが「まだ台風は続いている」と表示し続ける。

したがって速度は④が決める自由な数字ではない:

```
SpeedFor(activeDuration) = clamp(NominalPathLength / activeDuration, MinSpeed, MaxSpeed)
```

`activeDuration == 0`（＝プレハブが読めなかった）なら **0 を返す**。呼び出し側（T3）は速度 0 を「不明」として扱い、**台風を 1 個も起こさない**。これが設計書 §6 の「読めなければ推測せず何もしない」を構造で保証している唯一の場所である。**この `return 0f` を「安全な既定値」に書き換えてはいけない。**

### 1.3 強度の包絡線はバニラの落雷ランプと同じ形にする

`ThunderStormAI.SimulationStep` の落雷本数は `c = min(100, (f−act)>>3, (act+dur−f)>>3)` という**立ち上がり／立ち下がりの台形**で決まる（§A-1）。④の強度包絡線を別の形にすると、④が「今が最盛期」と表示している瞬間にバニラの落雷が減っている、という食い違いが起きる。**同じ台形にする**（`>>3` を `RampFraction = 0.25` の比で書き直したもの）。これは④が発明した数字ではなく、バニラの式に合わせた結果である —— 唯一、④の数字にバニラ由来の根拠がある箇所なので、doc に明記する。

実装の要点:

- `BearingOf(seed)` = `DeterministicRandom.Unit(seed, 0x54595048u) * 2π`（`0x54595048` は `"TYPH"`。マジックナンバーには由来をコメントで書く）

  ```
  R  = StormRadiusOf(intensity, prefabRadius);  if (R <= 0) return 0;
  G  = R * GaleFactor;
  d  = distance;  if (NaN || d < 0 || d >= G) return 0;
  eye  = R * EyeFraction;
  wall = R * WallFraction;
  if (d <= eye)  return EyeWind + (1f - EyeWind) * (d / eye);          // 眼の中は弱い
  if (d <= wall) return EyeWind + (1f - EyeWind) * ... → wall で 1f      // 壁雲へ立ち上がる
  else           return 1f - (d - wall) / (G - wall);                   // 外へ線形に減衰
  ```

```csharp
public void OnSimulationTick(uint frameIndex, float deltaMinutes)
{
    if (!ModSettings.TyphoonEnabled.value) return;

    // ここまでが「読んで publish するだけ」。ポーズ中もここは通る。
    var snapshot = TyphoonReader.Read();
    TyphoonHub.Publish(snapshot);

    if (Log.DiagEnabled(DisasterPlus.Core.Diagnostics.LogChannel.Typhoon))
    {
        Log.Diag(DisasterPlus.Core.Diagnostics.LogChannel.Typhoon, "typhoon",
            snapshot.Valid
                ? "prefab=" + (snapshot.Prefab.Usable ? "usable" : "UNUSABLE")
                  + " rain=" + snapshot.Rain.ToString("F2")
                  + " cloud=" + snapshot.Cloud.ToString("F2")
                : "snapshot invalid");
    }

    // ★ ここから下は状態を進める。ポーズ中（deltaMinutes == 0）は絶対に通さない。
    //    T3〜T10 が足す処理は必ずこの行より下に置くこと。
    //    このコメントを消すと「ポーズ中に台風が動き、建物が倒れ、川が溢れる」が起きる。
    if (deltaMinutes <= 0f) return;
```

### 3.1 台風はプレイヤーが明示的に起こす（設計書に無い決定）

設計書は「バニラの災害スロットを 1 つ取り、`ThunderStormAI` を土台にする」とだけ書いていて、**何が台風を始めるのかを決めていない**。取りうる案は 2 つあった:

| 案 | 判定 |
|---|---|
| (a) パネルの「台風を発生させる」ボタン（main → 依頼 → sim が実行） | **採用** |
| (b) バニラの雷雨災害を見つけて台風に昇格させる | **却下** |

(b) を却下する理由は §A-3 にある。`m_currentRain > 0.8` かつ落雷キューが空だと、**ゲームは自分で `ThunderStormAI` の災害を作る**。台風が雨を上げれば必ずその条件に入るので、(b) は「④が上げた雨がゲームに雷雨を作らせ、それを④が台風に昇格させ、その台風がまた雨を上げる」という自己増殖になる。しかもプレイヤーから見れば**災害パネルで雷雨を選んだだけで台風が来る**ことになり、原因が MOD だと気付く手段が無い。

したがって:

- パネルに「台風を発生させる」「台風を止める」の 2 ボタンを置く（T5）
- main スレッドは `TyphoonHub.Request(TyphoonRequest.Start)` を積むだけ
- sim スレッドの `TyphoonController.Tick` が `TakeRequest()` で拾って実行する
- **同時に 1 個だけ。** 既に Active なら `Start` は無視して理由を診断へ出す（災害スロット 256 を④が食い潰す形を作らない。②の `TsunamiChain` / `LongPeriodDamage` と同じ制限で、クラス doc に名乗る）

### 3.2 起こし方（罠 1 と罠 2 を両方踏まない手順）

`TsunamiChain.Raise` と `FireWhirlSpawner.TrySpawn` が既に写している `DisasterTool.<CreateDisaster>c__Iterator0` の手順そのまま（§E-3）:

```csharp
// ★ 前提: プレハブが使えること。使えないなら台風を起こさない（設計書 §6）。
if (!prefab.Usable) { _lastRefusal = "ThunderStormAI prefab values are unreadable"; return; }

float speed = TyphoonTrack.SpeedFor(prefab.ActiveDuration);
if (speed <= 0f) { _lastRefusal = "travel speed is unknown"; return; }

var info = DisasterManager.FindDisasterInfo<ThunderStormAI>();
if (info == null) { _lastRefusal = "no ThunderStormAI prefab (Natural Disasters DLC?)"; return; }

if (!Singleton<DisasterManager>.exists) { _lastRefusal = "DisasterManager is not available"; return; }
var manager = Singleton<DisasterManager>.instance;

ushort id;
// ★ 罠 2: 戻り値を必ず見る。false のとき id = 0 になり、そのまま書き込むと
//   **他人の災害スロットを書き潰す**（地震 §E-1、上限 256）。
if (!manager.CreateDisaster(out id, info))
{
    _lastRefusal = "CreateDisaster returned false (disaster buffer full?)";
    Log.Diag(DisasterPlus.Core.Diagnostics.LogChannel.Typhoon, "TyFull", _lastRefusal);
    return;
}

var buffer = manager.m_disasters.m_buffer;
var ai = info.m_disasterAI;

// 種は災害 ID。同じセーブなら同じ経路になる（設計書 §4.1）。
_seed = id;
_speed = speed;
_entryFrames = 0u;
_totalFrames = prefab.ActiveDuration;

Vec2 c0 = TyphoonTrack.CentreAt(_seed, 0u, _speed);
var pos = new Vector3(c0.X, 0f, c0.Z);
ai.ClampDisasterTarget(ref pos);          // public
pos.y = TerrainManager.instance.SampleDetailHeight(pos);   // StartDisaster と同じ扱い（§A-1）

buffer[id].m_targetPosition = pos;
buffer[id].m_angle = TyphoonTrack.HeadingAt(_seed, 0u, _speed);
buffer[id].m_intensity = ClampIntensity(ModSettings.TyphoonIntensity.value);
// ★ 罠 1: これが無いと StartDisaster は IL_000E で即 return する。
//   Significant(256) も付かず、周囲の建物が DetectDisaster を呼ばないので
//   **ハザードマップにも通知にも一切出ない**（§A-1）。③が実際にこれを出荷した。
buffer[id].m_flags |= DisasterData.Flags.SelfTrigger;

// StartDisaster は protected。CreateDisaster 直後の m_flags は Created(1) だけなので
// StartNow の & 60 の門は必ず通る（§E-3、③で IL 確認済み）。
ai.StartNow(id, ref buffer[id]);

// ★ SelfTrigger が本当に効いたかを、その場で確かめる。
//   StartDisaster が通っていれば m_activationFrame != 0 になっている（§A-1 IL_003F）。
if (buffer[id].m_activationFrame == 0u)
{
    _lastRefusal = "StartDisaster did not schedule an activation frame; "
                 + "the SelfTrigger flag did not take effect";
    Log.Error("typhoon: " + _lastRefusal, null);
    Stop();      // 作ったスロットを Clearing へ落として手放す
    return;
}
```

> **最後の 4 行が罠 1 の「構造で潰す」部分である。** フラグを立てるだけなら書き忘れをレビューで拾うしかないが、**立った結果を `m_activationFrame != 0` で観測**すれば、将来 `m_flags` の代入がリファクタで消えたときにも実行時に必ず気付く。②の Task 3 が `ActivationScheduled` を読み手側で用意した理由と同じ規律を、書き手側にも置く。

`ClampIntensity` は `Math.Max(10, Math.Min(255, value))` を `(byte)` へ。**キャストの前にクランプする**（`.cgs` の値は公開契約なので範囲外が入っていても読み捨てない。②の `EarthquakeLongPeriodStrength` と同じ扱い）。

### 3.3 毎 tick やること

```
1. TakeRequest() を 1 回だけ呼ぶ（Start / Stop）
2. Active でなければ return
3. 災害スロットがまだ自分のものか検証する（下記 3.4）
4. _elapsedFrames += (frame - _lastFrame)   ※ ポーズ中はここへ来ない
5. centre  = TyphoonTrack.CentreAt(seed, elapsed, speed)          ← 閉じた式
   heading = TyphoonTrack.HeadingAt(seed, elapsed, speed)
6. overLand = !TerrainManager.instance.HasWater(new Vector2(centre.X, centre.Z))
   decay    = TyphoonTrack.DecayAfter(decay, overLand, deltaMinutes)
   intensity = TyphoonTrack.IntensityAt(peak, elapsed, total, decay)
7. clamped = centre を ClampDisasterTarget で丸めたもの
   buffer[id].m_targetPosition = clamped
   buffer[id].m_angle          = heading
   buffer[id].m_intensity      = intensity
8. 終了判定（下記 3.5）
```

**④は「本当の中心」を自分で持ち、`m_targetPosition` にはクランプした写しを書く。** `ClampDisasterTarget` はマップ内に丸めるので、これを④の状態にすると台風がマップの縁に貼り付いたまま永久に終わらなくなる。終了判定は必ず**クランプ前**の `centre` で行う。

**`HasWater(Vector2)` は sim スレッド専用**（`WaterSimulation.BeginRead()/EndRead()` を取る。②が IL 実測済みで `TsunamiChain.IsUnderWater` に doc がある）。引数は**ワールド XZ**。

### 3.4 スロットの所有権を毎 tick 検証する

災害 ID は解放後に再利用される。④が掴んでいる `id` が別の災害に化けたまま `m_targetPosition` を書き続けると、**無関係な災害を④が引きずり回す**（③の `FireWhirlPinner` が距離で偽陽性を弾いているのと同じ事故）。毎 tick 次を確認し、1 つでも外れたら**書き込みをやめて `Forget()`**（`Stop()` ではない —— もう④のものではないので触ってはいけない）:

- `id != 0 && id < buffer.Length`
- `(buffer[id].m_flags & DisasterData.Flags.Created) != 0`
- `buffer[id].Info` が非 null で `Info.m_disasterAI is ThunderStormAI`（**要素ごとに try/catch**。`get_Info` は境界検査をしない、4 命令）
- `buffer[id].m_activationFrame == _activationFrame`（開始時に控えた値と一致するか。**再利用されたスロットを見分ける最も安いキー**）

外れたときは `Log.Diag(LogChannel.Typhoon, "TyLost", ...)` を 1 行出し、状態を `Refusal = "the disaster slot was reused by something else"` にする。**黙って手放さない。**

### 3.5 終わり方

終了条件は 3 つ。**どれで終わっても後始末は同じ 1 本の経路**（`Stop()`）を通す:

| 条件 | 意味 |
|---|---|
| `!TyphoonTrack.IsInsideMap(centre)` かつ `elapsed > 進入に要するフレーム数` | 台風が抜けた |
| `TyphoonTrack.PhaseAt(elapsed, total) == TyphoonPhase.Gone` | 持続時間を使い切った（＝ `m_activeDuration`） |
| `TakeRequest() == Stop` | プレイヤーが止めた |

`Stop()` がやること:


### 4.1 何を毎 tick 書くのか

```csharp
var w = Singleton<WeatherManager>.instance;   // exists を先に見る

// ★ 毎 tick 書く。再抽選は target == current のときにしか起きない（§A-4）ので、
//   毎 tick 書いていれば奪われない。1 回書いて放置すると、到達後に
//   1/20000/step で勝手に別の値へ振り直される。
```

`rain` / `cloud` は台風の位相と、**都市（マップ原点）から見た台風の距離**から出す:

```
near = 1 - clamp01(distanceToOrigin / galeRadius)      // 強風域に入るほど 1 へ
rain  = clamp(0.35 + 0.65 * near, 0, 1)
cloud = clamp(0.55 + 0.45 * near, 0, 1)
```

### 4.2 バニラの嵐と競合する 1 tick（説明を doc に残す）

### 4.3 台風の急旋回は表現できない（設計書 §7 の誠実さの範囲）

### 6.1 キューは読めない。だから「見積もって譲る」

`m_lightningQueue` は private で、`InstanceManager.GetPosition` の switch にも Lightning の分岐が無い（§A-2b）。**④はキューの残量を読めない。** リフレクションで private フィールドを覗く手もあるが、それはこの MOD がまだ一度もやっていない種類の依存で、しかもキューは水シミュではなく sim スレッドが毎ステップ詰め直す（§A-3）ので、覗いた瞬間の値には意味が薄い。

代わりに**両側を計算で押さえる**:

1. **④が撃ったぶん**は④が数える。`(scheduledFrame)` の配列を持ち、`HasExpired` で落とす。これは正確
2. **バニラの宿主が撃つぶん**は式から**上限**が出る（§A-1）:
   ```
   c = min(100, (f − act) >> 3, (act + dur − f) >> 3)
   c = (c * intensity + 50) / 100
   n = r.Int32(max(1, c/20), max(1, 1 + c/10))     ← 乱数だが、上限は max(1, 1 + c/10)
   ```
   **`m_randomSeed` を読まなくても上限が出せる**のが要点。intensity と `m_activationFrame` と `m_activeDuration` は④が全部知っている（T2 で実測、T3 で保持）
3. ④の取り分は `Allowance(inFlight, vanillaReserve) = QueueCapacity − MinFreeSlots − vanillaReserve − inFlight`（負なら 0）

`MinFreeSlots = 2` は環境落雷（§A-3）に残す余地である。**ここを 0 にしない** —— 埋め切ると、雨が 0.8 を超えているのにキューが空にならないので環境落雷は起きないが、代わりに**ゲーム側の `QueueLightningStrike` が常に false を返す状態**になり、他 MOD の落雷まで消える。

### 6.2 環境落雷はどちらに倒すか（設計書 §4.2 の「意識的に選ぶ」）

§A-3: `m_currentRain > 0.8 && m_lightningQueue.m_size == 0` のとき、ゲームは**新しい雷雨災害を作る**（`CreateDisaster` → `m_intensity = 10` → `StartNow` → `ActivateNow`、SelfTrigger 無し）。

- ④は台風の全期間にわたって雨を 0.8 以上に保つ（T4）
- **④が落雷を撒き続ける限り、キューが空にならないのでこれは起きない**
- 逆に「雨だけ上げて落雷を撒かない」設計にすると、**災害スロットに知らない雷雨が増え続ける**

**④は「撒き続ける」に倒す。** そのために `Tick` は**台風が Active の全期間、毎 tick 少なくとも 1 発の予定を持つ**ようにする（`inFlight == 0` になったら必ず補充する）。この判断を `TyphoonLightning` の doc に書き、診断に `queue kept non-empty: environmental lightning suppressed` を出す。

### 6.3 撒き方

```csharp
// 落着点は壁雲に偏らせる（実際の台風の構造。設計書 §4.2）。
float angle = DeterministicRandom.Unit(seed, salt) * 6.2831855f;
float band  = TyphoonProfile.EyeFraction
            + DeterministicRandom.Unit(seed, salt + 1u)
              * (TyphoonProfile.WallFraction * 1.3f - TyphoonProfile.EyeFraction);
float d = stormRadius * band;

var p = new Vector3(centre.X + cos(angle) * d, 0f, centre.Z + sin(angle) * d);
// §A-1 が ThunderStormAI 自身で使っている高さ取得。sim スレッド。
p.y = TerrainManager.instance.SampleRawHeightSmoothWithWater(p, false, 0f);

// §A-1 と同じ姿勢の作り方。
var q = Quaternion.AngleAxis(DeterministicRandom.Unit(seed, salt + 2u) * 360f, Vector3.up)
      * Quaternion.AngleAxis(DeterministicRandom.Unit(seed, salt + 3u) * 30f - 15f, Vector3.right);

// 遅延は 0..MaxDelayFrames。EarliestFrame より手前は切り上げられる（§A-3）ので、
// 自分で足しておく（そうしないと④の帳簿と実際の発火フレームがずれる）。
uint when = LightningBudget.EarliestFrame(frame)
          + (uint)(DeterministicRandom.Unit(seed, salt + 4u) * LightningBudget.MaxDelayFrames);

// ★ 戻り値を必ず見る。false は「キューが満杯で捨てられた」の唯一の合図（§A-3）。
if (weather.QueueLightningStrike(when, p, q, group)) { record(when); queued++; }
else rejected++;
```

### 7.1 既定 ON にする理由（②の第 2 層とは判断が違う）

②の第 2 層（津波連鎖・長周期地震動）は**既定 OFF** だった。理由は「バニラに存在しない挙動を既定で入れると、プレイヤーは地震のあと勝手に津波が来る原因が MOD だと気付く手段を持たない」。

**④にはその問題が無い。** 台風はプレイヤーが「台風を発生させる」ボタンを明示的に押さないと 1 個も起きない（T3 §3.1）。押した直後に起きることはすべて台風に帰属し、原因の取り違えようが無い。設計書 §4.3 も「④を有効にした時点でプレイヤーは新現象を求めている」として明示的に**既定 ON** を指定している。

**ただし強度は設定可能にする**（`TyphoonWindStrength`、0 で完全に無効）。②の `EarthquakeLongPeriodStrength` と同じ形。

### 7.2 モデル（全て④が発明した数字。定数名でそれが分かるようにする）

```
風速相当     wind = TyphoonProfile.WindAt(distance, intensity, prefabRadius)   ∈ [0,1]
建物係数     HeightFactor(h) = 1 + HeightBonus * clamp01((h - 10) / (70 - 10))
倒壊確率     CollapseChance = clamp(
                 (wind - MinWind) / (1 - MinWind)
                 * HeightFactor(h)
                 * (strength / 10)
                 * MaxCollapseChance,
                 0, MaxCollapseChance * (1 + HeightBonus))
```

- `wind < MinWind = 0.25` の建物は対象外。**「強風域の縁で家が飛ぶ」を作らない**
- `MaxCollapseChance = 0.05`。バニラの全体円盤（地震）が `0.02`、②の長周期が `0.25` なのに対して中間。**1 回の走査あたり**の確率で、走査は 256 フレームに 1 回なので、台風の全期間では十分に積み上がる
- **高さは「係数」であって「足切り」ではない。** ②の長周期は「高さが読めなければ何もしない」だったが、④の風害は違う: 台風は平屋も飛ばす。**高さが読めない（`BuildingHeight.MetresOf` が 0）建物には `HeightFactor = 1`（ボーナス無し）を使い、基本確率では対象に残す。** これは高さを推測しているのではなく、**ボーナスの適用を辞退している**。読めなかった件数は診断に出す（`LastUnknownHeight`）
- **これらは物理定数ではない。** 実在の建築や気象の値を名乗らない。doc に明記する

### 7.3 被害の与え方（NDR と正面衝突しないための線）

**`DisasterHelpers.DestroyBuildings` / `DestroyNetSegments` / `DestroyStuff` を絶対に呼ばない**（§F-1）。NDR はこの 2 つ（＋前者を呼ぶ `DestroyStuff`）を Prefix で完全置換し、`burnRadiusMin == 0 && burnRadiusMax == 0` を「竜巻だ」、`probability == 0.02f` を「地震だ」と嗅ぎ分ける。`BuildingAI.CollapseBuilding` を直接呼べばパッチ面 2 つを**完全に迂回できる**。

```csharp
var group = GroupOf(typhoonId);   // LongPeriodDamage.GroupOf と同じ形

// dry-run で「バニラが設計上受け付けるか」を実物に訊く。条件を自前で写さない。
accepted = ai.CollapseBuilding(id, ref buildings[id], group,
                               testOnly: true, demolish: false, burnAmount: 0);

// ★ dry-run が false でも本番は必ず呼ぶ。PowerPoleAI / CableCarPylonAI は
//   `if (testOnly) return false;` の直後に本物の倒壊を行う（§F-2）。
//   dry-run を信じて呼ばないと、実際には壊せる送電柱を取りこぼす。
if (ai.CollapseBuilding(id, ref buildings[id], group, false, false, 0)) collapsed++;
if (accepted) attempted++; else refused++;
```

**`burnAmount` は 0。** 風は「吹き飛ばして潰す」であって焼損ではない。

> **罠 5。`Building.m_fireIntensity` を直接書かない。** このフィールドを消費するのは `CommonBuildingAI` の系だけで、それ以外の AI に書き込むと誰も消さない永久の幽霊火災になり、**バニラの建物配列に入るのでセーブに焼き付き、MOD を外しても残る**。本プロジェクトは一度これを出荷している。火勢の面倒は `BurnBuilding` / `CollapseBuilding` に任せる。
> **レビューの grep:** `m_fireIntensity` が `src/DisasterPlus/Game/Typhoon/` に **0 件**であること。

**拒否する AI はそのままにする**（§F-2）。`demolish: false` では Shelter / DoomsdayVault / DamPowerHouse / DecorationBuilding / TsunamiBuoy が黙って false を返す。**防災施設が台風で壊れないのは正しい挙動なので、`demolish: true` へ逃げない。** これらは `refused` に積まれるので、診断で「壊れていない」と「壊せない」が区別できる。

**選定に使う乱数は `DeterministicRandom`**（`VanillaRandomizer` ではない）。これは④が発明した判断であり、バニラが引く値と一致する必要が無い。

```csharp
float roll = DeterministicRandom.Unit(typhoonId, buildingId);
```

**`frame` を混ぜない。** 混ぜると同じ建物が走査のたびに抽選し直され、時間とともに壊れる建物が際限なく増える（②の `LongPeriodDamage.IsSelected` と同じ注記）。

> ただし④は②と違い**中心が動く**。台風が近づけば同じ建物の `wind` が上がり、`roll` は固定でも `chance` が上がるので、いずれ閾値を超えて倒れる。**これが「台風が来ると被害が広がる」の実装であり、乱数にフレームを混ぜる必要が無い理由でもある。** doc に書く。

### 8.1 成立する唯一のルート

`m_type == TYPE_NATURAL(1)` の水源は**目標水位 `m_target` まで注ぎ、超えたら吸い戻す自己調整の泉**である（§D-4）。しかも吐き出し側のループは `natural && terrain[i] >= m_target` のセルを**スキップする**（IL_1E5E / IL_1EBF）ので、**丘の上には水を載せず、谷筋だけが濡れる**。これは河川氾濫そのものである。

マップの川は `WaterTool.PlaceSource` が置いたこの型の水源で流れている。したがって:

```
1. WaterSimulation.m_waterSources（public FastList）を走査する
2. m_type == TYPE_NATURAL(1) かつ台風の進路近傍のものを集める
3. 元の m_target を④が保存する          ← 罠 4
4. m_target += Δ（Δ は台風の強度と降雨量から）
5. 台風の通過後、元の値へ戻す。水は吸い込み側が自然に引かせる
```

**新しい水源は作らない**（設計書 §2 が (i) を選び (ii) を代案としている）。`CreateWaterSource` を呼ばなければ、罠 2 の「上限 65535 で false」も「注いだ水が引かない」も最初から発生しない。**この判断を doc に書く**（次の担当者が「もっと強い氾濫を」と `CreateWaterSource` に手を伸ばすのを止めるため）。

`DisasterHelpers.SplashWater`（`TYPE_IMPACT` の波、`m_duration = 256` で自動解放）を演出として重ねてもよいが、**体積は増えないのでこれ単独では氾濫にならない**（§D-3(b)）。**本タスクでは足さない** —— 水面の見た目より、`m_target` の復元を確実にすることを優先する。

### 8.3 ロックの取り方（罠 3）

```csharp
// ★ LockWaterSource は Monitor を取ったまま返る（§D-4、IL_0005–002E に Monitor.Exit が無い）。
//   UnlockWaterSource が唯一の解放経路。**必ず try/finally で対にする。**
//   落とすと水シミュ専用スレッドがスピンロックで固まり、ゲームが無反応になる。
WaterSource src = sim.LockWaterSource(handle);
try
{
    if (src.m_type != TypeNatural) return;   // ★ return しても finally は必ず走る
    src.m_target = FloodTarget.RaisedTarget(original, rise);
}
finally
{
    sim.UnlockWaterSource(handle, src);
}
```

**`try` の中で例外を投げうる処理を増やさない。** ログも診断カウンタの更新も `finally` の**外**でやる。`Log.Diag` は内部で `lock` を取るので、水源のモニタを握ったまま呼ぶと**2 本のロックの取得順**という、この MOD がまだ一度も抱えていない種類の問題を作ることになる。

**走査そのものは `m_waterSources` を直接読む**（public FastList）。ロックを取るのは**書き換える 1 個ずつ**にする。全件をロックの中で回すと、水スレッドが 1 ステップぶん止まる。

### 8.4 復元（罠 4）— **3 箇所から呼ぶ**

`Dictionary<ushort, ushort> _originalTargets`（ハンドル → 元の `m_target`）を持つ。復元は `RestoreAll()` 1 本にまとめ、**次の 3 箇所から呼ぶ**:

### 8.5 保存時の復元と、**再適用を遅らせる**（本プロジェクトが一度踏んだ罠）

水源は `WaterSimulation.Data.Serialize` でセーブに焼き付く（§D-4）。台風の最中にプレイヤーがセーブすると、**そのセーブには持ち上げた `m_target` が入る**。MOD を外してそのセーブを開けば、川は永久に溢れたままになる。

本プロジェクトは**これと同じ形の失敗を一度出荷している**（一時フラグがセーブに漏れた件）。そのとき確定した事実は:

> **MOD の `OnSaveData` はバニラの配列書き込みより先に走る。** したがって
> 「`OnSaveData` の中で clear → `finally` で再適用」では**漏れる**。
> 再適用は `SimulationManager.AddAction` で**遅延させる**必要がある。

したがって:

```csharp
// DisasterPlusSerialization.OnSaveData の先頭
// ★ 水源の m_target は WaterSimulation.Data.Serialize でセーブに焼き付く（§D-4）。
//   MOD を外したセーブで川が溢れたままにならないよう、保存の前に必ず戻す。
var raised = TyphoonFlood.SnapshotAndRestoreForSave();   // 戻した内容を控えて返す

// ★ 再適用は AddAction で遅らせる。ここで（あるいは finally で）すぐ戻すと、
//   バニラが配列を書く前に持ち上げ直すことになり、漏れが再発する。
if (raised != null)
{
    SimulationManager.instance.AddAction(delegate { TyphoonFlood.ReapplyAfterSave(raised); });
}
```

`SnapshotAndRestoreForSave()` は「今持ち上げているぶんを元に戻し、その内容を返す」。`ReapplyAfterSave(list)` は「台風がまだ Active なら持ち上げ直す。終わっていれば何もしない」。**`ReapplyAfterSave` は sim スレッドで走る**（`AddAction` の契約）。

> **`AddAction` のシグネチャと public 性を Step 1 の IL 確認に含めること。** この経路は本プロジェクトの記憶にはあるが、④の事実文書には無い。

### 9.1 `Core` に置けるのは「頂点の座標」だけ

`Core/` は `UnityEngine` を参照できない。したがって `SpiralMesh` は**配列を埋めるだけ**にし、`Mesh` の組み立ては `Game/` 側で行う（設計書 §5 が明示している）。

- 呼び出し側が配列を確保して渡す（`Build` が `new` しない）。**毎フレーム呼ばれる型ではない**が、`Core/` の他の型と同じく割り当てを持たない形に揃える
- `uvs` は `float[]`（`Vec2[]` でもよいが、`Mesh.uv` は `Vector2[]` なので詰め替えが 1 回で済む `float[]`（u, v の交互）にする）
- 手本は `VortexAI.GenerateMesh()`（§C-1）: 16250 頂点・高さ 2000・下端半径 50・上端半径 200 の漏斗を、`Randomizer(2975689)` の固定シードで手続き生成している。**同じ作り方で水平の渦巻きを組む**

### 10.2 操舵（③の `FireWhirlPinner` と同じ経路、向きだけ違う）

竜巻は「災害」ではなく **`VortexAI` の車両が動く**（§E-1）。`m_targetPosition` を書いても車両は追随しない。

