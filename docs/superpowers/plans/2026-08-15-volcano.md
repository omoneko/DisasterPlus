# ⑤火山 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** クリックした地点で、範囲内の道路と建物を段階的に壊しながら地面が隆起し、山頂の火口から噴火して溶岩が斜面を流れ下り、通った跡に火災を起こす**火山**を作る。地形の変化は不可逆であり、その事実を配置の前にプレイヤーへ示す。

**Architecture:** ⑤は**バニラの災害スロットに載らない**（設計書 §2）。ND DLC 無しでは `DisasterInfo` プレハブが 1 つも存在せず（事実文書 §D-11）、自前プレハブの実行時登録はセーブにプレハブ名を焼き込む。したがって⑤は自前の位相機械（`VolcanoState`）で動く。地形は sim スレッドが `TerrainManager.RawHeights` を直接書き、`TerrainModify.UpdateArea` を**自分で分割して**呼ぶ（§A-1）。**準備（破壊）が隆起より必ず先行する** —— 道路と建物は毎フラッシュ地形を自分の高さへ押し戻すので（§A-2）、順序を逆にすると山の中に平らな溝とすり鉢ができる。読み取りは sim、UI と描画は main で、①②④と同じ snapshot-then-render（単一の素の `lock`）で渡す。溶岩の描画だけは main スレッドの `Graphics.DrawMesh` で、他のどの要素からも依存されない単独タスクにする。

**Tech Stack:** C# 7.3 / .NET Framework 3.5、Unity 5.6、ColossalFramework UI、xunit / net8.0（Core テスト）、MSBuild。

**Spec:** `docs/superpowers/specs/2026-08-15-volcano-design.md`

## Global Constraints

- **.NET Framework 3.5 / C# 7.3**、Unity 5.6。C# 8+ 構文（switch 式、`??=`、範囲演算子、`using` 宣言、null 許容参照型）は**コンパイルエラー**になる。Unity 5.6 以降に追加された API は存在しない
- `Core/` はエンジン非依存。**`UnityEngine` 不可、Cities API 不可、`System.Random` 不可、LINQ 不可。** net35 の MOD と net8.0 の xunit テストプロジェクトの**両方**にコンパイルされる（dual-target）
- net35 に **`System.Collections.Concurrent` は無い。** 共有状態は単一の素の `lock`
- **スレッド境界**: `TerrainManager` / `BuildingManager` / `NetManager` / `DisasterManager` と全ゲームバッファは **sim スレッド**が所有する。`UIComponent` / ツール / `Graphics.DrawMesh` は **main スレッド**が所有する。境界を破るとスタックトレースの無い `IndexOutOfRangeException` が**後から**バニラのコードの中で出る。確立した型は snapshot-then-render（単一の素の `lock`）
- **乱数は `DeterministicRandom` だけを使う。** `VanillaRandomizer` は「バニラが実際に引く値と一致させる」ためだけのもので、**⑤はそういう引きを 1 つもしない**
- 名前空間は `Game/` が `DisasterPlus.Game`（サブフォルダに関わらず）、`Core/` が `DisasterPlus.Core.*`。**この MOD の `LogChannel` は常に完全修飾する** — `Assembly-CSharp` がグローバル名前空間に同名の型を宣言している
- `Strings` / `Locales/en.txt` / `Locales/ja.txt` のキー集合は常に一致させる（**現在 212**）。追加したら `tools/GenerateLocaleTemplate.ps1` で `en.txt` を再生成する。`Locales/*.txt` は UTF-8 **BOM なし**。**`.ps1` は ASCII のみにする**
- 保存設定は公開契約。**キーは足すだけで、既存のキー番号もビット値も詰め直さない**
- 全セッション状態はレベルアンロードでリセットする。**2 つ目の都市がきれいにロードできること**（メッシュとマテリアルは破棄する）
- `Log.Warn` / `Log.Error` はスロットルされない。**毎フレーム・毎 sim tick の経路に置かない**
- フレーム → 時間の換算は **`FeatureHost.FramesPerMinute` から出す**。定数を直書きしない
- ビルド: `powershell -ExecutionPolicy Bypass -File build.ps1`、**警告 0**。テスト: `dotnet test tests/DisasterPlus.Core.Tests/DisasterPlus.Core.Tests.csproj`（**現在 350 件緑**）。**800 行を超えるファイルを作らない**
- **PowerShell の `Get-Content -Raw` → `Set-Content` でファイルを編集しない**（日本語が化ける）。Write/Edit ツールを使う
- コミットは `<type>: <説明>` 形式（feat/fix/docs/test/chore/refactor）。説明は**日本語**
- ブランチは `feature/volcano`（**④台風が master にマージされた後の master から作る**）。**コミットのみ。push もマージもしない**

## ⑤の表示規約（④と同じ。全タスク共通）

①はバニラが既に計算していたハザードマップを見せ、②はバニラが既に持っていた決定論的な被害モデルを見せた。**⑤にその原資は無い** —— 溶岩は文字列ヒープにすら存在せず（§B-5）、火山という現象もバニラには無い。設計書 §7.4 が「⑤の数値は原則すべて本 MOD のものである。**④と同じ扱いで、見出しで一度言う**」と明示している。

| | ⑤の規約 |
|---|---|
| 原則 | **⑤が出す数値は全て本 MOD のものである。** パネルの見出しで**一度だけ**言う（`Strings.VolcanoModelHeader`） |
| 行ごとの印 | **付けない** |
| 唯一の例外 | **ゲームの配列から読んだだけで⑤が何も計算していない値**、すなわち (a) 設置地点の地形高さ（`SampleDetailHeight`）と (b) 影響範囲の建物数・道路セグメント数（グリッド走査の実数）。この 2 種類にだけ `Strings.SourceVanilla`（`[measured]`）を付ける |
| `Strings.SourceModel` | **`Game/Volcano/` と `Game/UI/VolcanoPanelButton.cs` / `VolcanoPlacementTool.cs` に 1 度も現れてはいけない** |

**機械的に確認できる形にする**（タスク 3 で導入し、以後のタスクは守るだけ）:

1. `UILabel` を作ってよいのは `VolcanoRows.AddLabel` の 1 箇所だけ。公開するのは `AddTitleRow` / `AddSectionHeader` / `AddRow` / `AddRow(height)` / `AddMeasuredRow` の 5 系統
2. `UILabel.text` への代入が現れるのは `VolcanoRows.SetPlain` の 1 箇所だけ
3. `Strings.SourceVanilla` が現れるのは `VolcanoRows.SetMeasured` の中だけ。**接頭辞は呼び出し側に選ばせない**
4. `SetMeasured` を呼んでよいのは**設置地点の地形高さ・建物数・道路セグメント数の 3 行だけ**。それ以外の行が `[measured]` を名乗ったら、⑤が「ゲームが計算した」と嘘をついている

**④の `TyphoonRows` を型として流用しない。** 設計書 §5 は「④の `TyphoonRows` を流用」と書いているが、あの型は `UILabel.name` に `"Typhoon"` を焼き込み、クラス doc が「`SetMeasured` を呼んでよいのは雨量と雲量の 2 行だけ」という**④固有の担保**を名乗っている。共有すると④のレビューが確定させた grep の担保を⑤の都合で作り直させることになる（②→④で同じ判断をしている）。**枠組み（定数・ヘルパーの形・grep で守る規律）を写して `VolcanoRows` を新設する。** これは設計書 §5 の意図（同じ見た目・同じ規約）を満たしたうえでの実装上の判断である。

## 出してよい断定の範囲（設計書 §7、全タスク共通）

1. **地形の変更は不可逆であると、配置の前に明示する。** バニラにアンドゥは無く、セーブに焼き付く（§E-13）。利用者は「不可逆でよい」と判断したが、**それはプレイヤーに黙っていてよいという意味ではない**（設計書 §7.1）。確認ダイアログの本文で名乗る（T4）
2. **破壊される道路と建物の概数を先に見せ、概数であることも明示する**（設計書 §7.2）。数えた時点の実数であること・準備が進む間に都市は変化しうることを書く（T4）
3. **建設可能判定と水位が数ゲーム内時間遅れることを説明する**（設計書 §7.3）。`m_blockHeights` はゲームモードで上へ 2 m / 64 sim フレームしか動かず、水シミュはその配列そのものを見ている（§A-2 / §A-4）。**これは不具合ではない。** 見積り値をパネルと診断に出す（T6）
4. **⑤の数値は原則すべて本 MOD のものである**（設計書 §7.4）。上の「⑤の表示規約」の節
5. **メートル毎秒・度・カロリーのような実在の物理単位を名乗らない。** 溶岩の「温度」も「粘性」も⑤は持っていない。出すのは距離（m）・高さ（m）・時間（ゲーム内分）・0〜10 の段階だけ

## 2 つの乱数生成器（②が定めた規則をそのまま適用する）

> その数字が「この MOD が発明した判断」を決めるなら `DeterministicRandom`。
> 「バニラが引く値と一致しなければならない」なら `VanillaRandomizer`。

**⑤が引く乱数は全て前者である。** 溶岩の本数も初期方向も噴出のゆらぎも⑤が発明した判断であって、バニラが引く値ではない。**⑤はバニラの災害スロットに載らないので、バニラの引きに同期すべき箇所が構造上 1 つも無い。** `Core/Earthquake/VanillaRandomizer` は⑤のコードから**1 度も参照しない**（レビューの grep: `src/DisasterPlus/Core/Volcano/` と `src/DisasterPlus/Game/Volcano/` に `VanillaRandomizer` が 0 件）。

**乱数にフレーム番号を混ぜない。** 混ぜると同じ対象が tick ごとに抽選し直され、時間とともに際限なく増える（②の `LongPeriodDamage.IsSelected` / ④の `TyphoonWind.IsSelected` と同じ注記）。⑤で「時間とともに広がる」のは、乱数ではなく**溶岩の先端が進むから**である。

## タスクの切り直しと、その理由

設計書 §8 は 7 段を挙げている。**順序は変えていない。** 変えたのは切り方だけである。

| §8 の段 | 本計画 | 理由 |
|---|---|---|
| 1（の一部） | **T1** Core の地形三点セット（形態・隆起スケジュール・矩形分割） | §8 段 1 は「形態・スケジュール・最急降下・分割」の 4 つを挙げているが、**最急降下（`LavaPath`）だけは 4 段あとの溶岩タスクにしか使われない**。④が `SpiralMesh` を雲のタスクに置いたのと同じ扱いで、Core の型は**唯一の消費者の隣**に置く。残る 3 つは⑤の地形の正しさそのもので、罠 2・3 が全部ここに掛かる。単独のレビュー関門になる |
| 2（の一部） | **T2** 骨格・地形 API の解決・診断 | ②の Task 3・④の T2 と同じ「パネルの無い機能」。都市をロードすると診断ダンプに地形の実測（配列長・セル・量子・天井までの余裕・ND 所持）が出るだけの成果物。**T3 以降の全部がこの上に乗る** |
| 2（の一部） | **T3** パネル・ボタン・表示規約 | §8 段 2 は「骨格・配置ツール・確認ダイアログ・前提検証」を 1 段にまとめているが、**確認ダイアログは行を持つ**ので、行の作り方を縛る `VolcanoRows`（⑤の表示規約）はそれより前に無ければならない。④が T5 で同じ順序にしている |
| 2（の残り） | **T4** 配置ツール・影響範囲の調査・不可逆の確認 | §8 段 2 の残り。**調査（読むだけ）と破壊（壊す）を別のタスクに割る**（下記） |
| 3 | **T5** 準備（道路と建物の段階的破壊） | §8 段 3 のまま。**Step 1 が道路の破壊経路を IL で確定させる**（設計書 付録が「未確定」と明示） |
| 4 | **T6** 隆起 | §8 段 4 のまま。**T5 の `ClearedRadiusMetres` を型で消費する**（罠 1） |
| 5 | **T7** 噴火 | §8 段 5 のまま |

| 7 | **T9** 溶岩の描画 | §8 段 7 のまま。**他のどのタスクからも依存されない**（下記） |

**§8 段 2 を「調査（T4）」と「破壊（T5）」に割った理由。** 設計書 §4.1 は「クリック後、破壊される道路と建物の概数を出して確認を取る」と要求している。概数を出すには**影響範囲の建物グリッドと道路グリッドを走査して数える**必要があり、それは準備段の走査と同じ形をしている。だが**「数える」と「壊す」は、レビュー関門として別物である** —— 「数えられるし、プレイヤーに訊いてから進む」を承認しながら「壊し方」を差し戻せる。加えて、**道路の破壊経路（`NetAI.CollapseSegment` の `demolish:true` の実効）は未確定**（設計書 付録）であり、T4 を先に閉じておけば、T5 の Step 1 が「読めなかったら⑤は隆起を始めない」という結論を出しても T4 の成果物は無傷で残る。

**T5（準備）→ T6（隆起）の依存を、注記ではなく型にする。**

- `VolcanoClearing` は `public static float ClearedRadiusMetres { get; }` を出す（まだ 1 本も壊していなければ **0**）
- `VolcanoUplift` が書いてよいセルは `UpliftSchedule.ActiveRadiusMetres(shapeRadius, VolcanoClearing.ClearedRadiusMetres)` の内側だけ。**この関数は Core にあり、`clearedRadius` が 0 なら 0 を返すことをテストが固定している**（T1）
- **`VolcanoUplift.cs` の中で `VolcanoClearing.ClearedRadiusMetres` 以外の半径を `UpliftSchedule.ActiveRadiusMetres` に渡してはいけない。** レビューの grep: `ActiveRadiusMetres` の呼び出しが 1 箇所で、第 2 引数が `VolcanoClearing.ClearedRadiusMetres` であること
- **T6 を T5 より先に実装してはいけない。** T6 の実装者は `VolcanoClearing.ClearedRadiusMetres` が存在することを前提にできる

### 1.1 隆起は「増分」ではなく「絶対目標」にする（罠 2 の潰し方）

素朴な実装は `raw[i] += step` である。これは**必ず無言で壊れる**。`RawHeights` は `ushort` の `raw/64` メートルで、`MakeCrater` も `MakeCrack` も `if (n != raw)` で書き込みを省く（§C-8）。したがって 1 tick の増分がセル高さで 1/64 m = 0.015625 m を下回ると**丸めで消え、そのセルは永久に動かない**。外周のセルは中心より遅く上がるので、素朴な実装では**山の裾だけが最初から完全に停止する**。例外は出ない。

そこで⑤は**その時刻における絶対目標**を毎 tick 計算して書く:

```
rawTarget(cell, t) = baseRaw(cell) + round( profile(distance) * progress(t) * 64 )
```

こうすると、まだ 1 raw 単位に届かないセルは**書かれないだけで、進捗は `progress` という float に蓄積されている**。届いた瞬間に 1 段上がる。裾は階段状に上がるが、これは 16 m 格子の下では正しい挙動であり、`SmoothSample` が補間するので見た目には出ない（§C-9）。

**それでも 1 つだけ守らなければならない下限がある。** 山頂（`profile = H`）が 1 tick に 1 raw 単位も動かないと、隆起そのものが止まって見える。`TotalTicksFor` が `requestedTicks` を `H × 64` で切り詰めることで、これを構造的に保証する。**この切り詰めを「余計なお世話」だと思って外してはいけない。**

### 1.2 分割は⑤の責任である（罠 3 の潰し方）

`TerrainModify.UpdateArea` は**矩形が 128×128 raw セルを超えるとタイル分割せずに切り捨てる**（§A-1 の `Min(m_maxX, m_minX + 120 + 8)`）。はみ出した部分は更新されないまま残る。加えて**単発の要求面積が 10000 セルを超えると、入れ子のバッチを無視して即フラッシュする**（§A-1 / §D-12）。

`TileSplit` はこの 2 つの制約を**同時に**満たす。ここで見落としやすいのは、**判定に掛かるのは `UpdateArea` に実際に渡した矩形であって、⑤が内心思っているタイルではない**という点である。`MakeCrater` / `MakeCrack` と同じく境目に段差を作らないため、⑤は各タイルを `±Margin`（2 セル）だけ広げて渡す。したがって:

```
CoreTileSide (95) + 2 * Margin (2) = MaxPassedSide (99)
MaxPassedSide² = 9801 セル  <  10000（強制フラッシュの閾値）
MaxPassedSide  =   99      <  128 （無言切り捨ての閾値）
```

**`TileAt` は「渡す矩形」を返す。** 呼び出し側が margin を足し直してはいけない（足すと 103×103 = 10609 セルになり、10000 の閾値を跨いで毎回フラッシュする）。テストが**返ってきた矩形そのもの**を測っている理由がこれである。

### 1.3 3 形態は「高さプロファイルの違いだけ」（設計書 §2）

| 形態 | プロファイル `h(d)`（`u = d / (0.837R)`） | 既定 R / H | 平均勾配 |
|---|---|---|---|
| 盾状 `Shield` | `d < 0.73R`: `H(1 − u⁴)` / `0.73R ≤ d < R`: `4H(u − 1.197)²` | 2000 m / 200 m | 1 : 10 |
| 成層 `Strato` | `H(1 − d/R)` | 1200 m / 600 m | 1 : 2 |
| 溶岩ドーム `Dome` | `H(1 − (d/R)²)²` | 350 m / 300 m | 1 : 1.17 |

**盾状のプロファイルは `MakeCrater(pos, R, −H, raiseEdges:false)` が描く形そのものである**（§C-8 の実測式をそのまま写した）。⑤はそれを**自分で書く** —— `MakeCrater` は呼ぶたびに `RefreshAllModifications()` で強制フラッシュするので（罠 4）、段階的隆起には使えないからである。形は同じで、コストだけが違う。**この経緯をクラス doc に書く**（次の担当者が「盾状は `MakeCrater` 1 発で済むのに、なぜ手で書いているのか」と言って戻すのを止めるため）。

**溶岩ドームの半径は 250 m を下回らせない**（§C-9）。片側 8 raw セルであり、それ以下は「山」ではなく地面のノイズに見える。`MinRadiusOf(Dome)` が 250 を返し、`RadiusFor` がクランプする。

### 1.4 天井は例外を出さずに山頂を平らにする（§C-10）

`RawHeights` の表現上限は `65535 / 64 = 1023.984375 m` で、**超えても例外は出ず `Clamp(…, 0, 65535)` で無言に頭打ちになり、山頂が平らな台地になる**。したがって⑤は**起点の地形高さを読んでから最大高を決める**。`HeightFor` が

```
headroom = MaxTerrainMetres − baseHeightMetres − CraterRimHeadroomOf(h)
```

で切り、`HeightWasLimitedByCeiling` が「切ったかどうか」を別に返す。**T4 の確認ダイアログはこれを見て「この場所では 480 m までしか作れません」と先に言う。** 黙って低い山を作らない。

`CraterRimHeadroomOf` を引くのは、火口が `MakeCrater(summit, r, +d, raiseEdges:true)`（中心 −0.7d、0.75r に **+0.3d の縁**、§C-8）で彫られ、**縁が山頂より上に出る**ためである。ここを忘れると、天井ぎりぎりの山で火口の縁だけが無言で切られて円環が平らになる。

/// 3 形態の高さプロファイル。**ここにある数字は全て本 MOD が発明したものである。**

///

/// TerrainModify.RefreshAllModifications() を呼ぶ（§C-8 IL_0006）ため、
/// **呼ぶたびに地形の強制フラッシュが 1 回走る**。段階的隆起で毎 tick 呼べば
/// バニラのバッチ最適化を毎 tick 無効化することになる（§A-1 の設計上の結論 3）。
/// 形は同じで、コストだけが違う。**「MakeCrater 1 発で済む」と言って
/// 戻さないこと。** 山頂の火口だけは MakeCrater を 1 回使う（Game/Volcano/VolcanoUplift）。
///
/// 勾配クランプも侵食も平滑化パスも存在しない（§C-9）ので、急峻な円錐は潰れない。
/// 制約は「16 m 格子」と「1/64 m 量子」の 2 つだけである。だから
/// **溶岩ドームの半径を 250 m（片側 8 raw セル）より小さくしない**。
/// それ以下は「山」ではなく地面のノイズに見える。
///
/// 高さの天井は 65535/64 = 1023.984375 m で、**超えても例外は出ず無言で
/// 山頂が平らな台地になる**（§C-10）。<see cref="HeightFor"/> が起点の地形高さと
/// 火口の縁の分を先に引き、<see cref="HeightWasLimitedByCeiling"/> が
/// 「切ったかどうか」を別に返す。呼び出し側はそれをプレイヤーに先に見せること。
/// </summary>
```

実装の要点:

- `FormOf(int v)`: `0 → Shield` / `1 → Strato` / `2 → Dome` / それ以外 `Strato`（既定）
- 帯（`MinRadiusOf` / `MaxRadiusOf` / `DefaultRadiusOf` / `MinHeightOf` / `MaxHeightOf` / `DefaultHeightOf`）:

  | 形態 | R 最小 | R 既定 | R 最大 | H 最小 | H 既定 | H 最大 |
  |---|---|---|---|---|---|---|
  | `Shield` | 800 | **2000** | 3000 | 50 | **200** | 300 |
  | `Strato` | 400 | **1200** | 2000 | 100 | **600** | 700 |
  | `Dome` | **250** | **350** | 800 | 100 | **300** | 400 |

- `RadiusFor(form, r)`: `NaN` は既定値。それ以外は帯へクランプ
- `HeadroomMetres(baseHeight)`: `NaN` なら 0。それ以外は `Max(0, MaxTerrainMetres − baseHeight)`
- `HeightFor(form, h, baseHeight)`:
  ```
  h = NaN ? DefaultHeightOf(form) : clamp(h, MinHeightOf, MaxHeightOf)
  limit = HeadroomMetres(baseHeight) − CraterRimHeadroomOf(h)
  return clamp(Min(h, limit), 0, MaxHeightOf(form))
  ```
  **`limit` が `MinHeightOf` を割ることはありうる**（標高 1000 m の山の上に置いた場合）。そのときは `MinHeightOf` を返さず、**そのまま小さい値を返す**。呼び出し側（T4）が `HeightWasLimitedByCeiling` を見て「この場所には作れません」と断る
- `HeightWasLimitedByCeiling(form, h, baseHeight)`: クランプ後の要求高より `HeightFor` の返り値が小さければ true
- `ProfileAt(form, d, R, H)`: `d`/`R`/`H` のいずれかが `NaN`、`d < 0`、`R <= 0`、`H <= 0`、`d >= R` なら **0**。それ以外:
  ```
  Shield : u = d / (ShieldFalloff * R)
           d < ShieldInnerFraction * R  →  H * (1 − u⁴)
           それ以外                      →  H * 4 * (u − ShieldOuterOffset)²
  Strato : H * (1 − d / R)
  Dome   : t = d / R ; H * (1 − t²)²
  ```
- `CraterRadiusOf(R)`: `NaN`/`<=0` は 0。それ以外 `clamp(R * 0.12f, 40f, 400f)`
- `CraterDepthOf(H)`: `NaN`/`<=0` は 0。それ以外 `clamp(H * 0.12f, 10f, 60f)`
- `CraterRimHeadroomOf(H)`: `0.3f * CraterDepthOf(H)`（§C-8 の `raiseEdges:true` は 0.75r に `+0.3×depth` の縁を作る）

/// <summary>
/// 隆起の進み方。**increment ではなく、その時刻における絶対目標を返す。**
///
/// 素朴な `raw[i] += step` は必ず無言で壊れる。RawHeights は ushort の raw/64 m で、
/// 書き込み側は `if (n != raw)` で省略する（§C-8）。1 tick の変化がセル高さで
/// 1/64 m = 0.015625 m を下回ると**丸めで消え、そのセルは永久に動かない**。
/// 外周ほど遅く上がるので、素朴な実装では**裾だけが最初から完全停止する**。
/// 例外は 1 つも出ない。
///
/// 絶対目標にすると、まだ 1 raw 単位に届かないセルは「書かれないだけ」で、
/// 進捗は progress という float に蓄積されている。届いた瞬間に 1 段上がる。
///
/// **それでも山頂だけは毎 tick 動かなければならない。** 動かなければ隆起そのものが
/// 止まって見えるからで、<see cref="TotalTicksFor"/> が要求 tick 数を H×64 で
/// 切り詰めることで構造的に保証している。**この切り詰めを外さないこと。**
///
/// <see cref="ActiveRadiusMetres"/> は⑤全体でいちばん重要な 1 行である。
/// **準備（道路と建物の破壊）が届いていない場所を持ち上げてはいけない。**
/// 道路は m_flattenTerrain のとき Heights.PrimaryLevel でセルを道路の y に
/// **強制固定**し、建物は SecondaryLevel で自分の y に固定する。しかもそれは
/// 毎フラッシュゼロからやり直される（§A-2）ので、**書き続けても勝てない**。
/// 準備を先にしないと、山の中に平らな溝とすり鉢が残る（設計書 §1.2）。
/// clearedRadius が 0（＝まだ 1 本も壊していない）なら 0 を返す。
/// **これを「制限なし」に読み替えてはいけない。**
///
/// <see cref="BlockHeightCatchUpFrames"/> は「建てられる地面」と水位が遅れる量である。
/// m_blockHeights はゲームモードで上へ 2 m / 64 sim フレームしか動かず（§A-2）、
/// WaterSimulation.m_heightBuffer はその配列そのもの（§A-4）。**これは不具合ではない。**
/// 呼び出し側はこの値をプレイヤーに説明すること（設計書 §7.3）。
/// </summary>
```

実装の要点:

- `TotalTicksFor(h, requested)`: `h` が `NaN`/`<=0` なら `Max(1, requested)`。それ以外 `maxTicks = (int)(h * RawUnitsPerMetre)`、`clamp(requested, 1, Max(1, maxTicks))`
- `ProgressAt(tick, total)`: `total <= 0` なら 0。`clamp(tick / (float)total, 0, 1)`
- `RawTargetAt(baseRaw, profileMetres, progress)`: `profileMetres` か `progress` が `NaN` なら `baseRaw`。それ以外
  ```
  delta = (int)Math.Round(profileMetres * clamp01ish(progress) * RawUnitsPerMetre)
  v = (int)baseRaw + delta
  return (ushort)clamp(v, 0, MaxRaw)     // ★ キャストの前に必ずクランプする
  ```
  **`progress` は `[0,1]` にクランプするが、`profileMetres` は負を許す**（テストが `0` への飽和を固定している）
- `ActiveRadiusMetres(shapeRadius, clearedRadius)`: どちらかが `NaN` か `<= 0` なら **0**。それ以外 `Min(shapeRadius, clearedRadius)`
- `ClearingFrontMetres(shapeRadius, progress, lead)`: `NaN` は 0。`Min(shapeRadius, shapeRadius * clamp01(progress) + Max(0, lead))`
- `BlockHeightCatchUpFrames(h)`: `NaN`/`<=0` は 0。`(int)Math.Ceiling(h / (BlockHeightRiseRawPerCycle / RawUnitsPerMetre)) * BlockHeightCycleFrames`（= `ceil(h / 2) * 64`）

/// TerrainModify.UpdateArea へ渡す矩形の分割。**分割は呼び出し側の責任である。**
///
/// UpdateArea は矩形が 128×128 raw セルを超えると、**タイル分割せずに無言で

///
///     CoreTileSide (95) + 2 * Margin (2) = MaxPassedSide (99)
///     99 &lt; 128        99*99 = 9801 &lt; 10000

/// **呼び出し側で margin を足し直さないこと**（足すと 103×103 = 10609 セルになり、

### 2.2 `IPausedTickFeature` を名乗る条件（T4 以降で破らないための約束）

`VolcanoFeature` は `IPausedTickFeature` を実装する。理由は①②④と同じ（ロード直後にポーズしたままパネルを開くと全行が「読み取れません」になる）。

**ただし⑤は T4 以降でゲームの状態を進める。しかも⑤が進めるのは地形であり、取り消せない。** `OnSimulationTick` を**このタスクで最初からこの形にする**:

```csharp
public void OnSimulationTick(uint frameIndex, float deltaMinutes)
{
    if (!ModSettings.VolcanoEnabled.value) return;

    // ここまでが「読んで publish するだけ」。ポーズ中もここは通る。
    var snapshot = VolcanoReader.Read();
    VolcanoHub.Publish(snapshot);

    if (Log.DiagEnabled(DisasterPlus.Core.Diagnostics.LogChannel.Volcano))
    {
        Log.Diag(DisasterPlus.Core.Diagnostics.LogChannel.Volcano, "volcano",
            snapshot.Valid
                ? "terrain=" + (snapshot.Terrain.Usable ? "usable" : "UNUSABLE")
                  + " raw=" + snapshot.Terrain.RawArrayLength
                : "snapshot invalid");
    }

    // ★ ここから下は状態を進める。⑤が進めるのは**取り消せない地形**である。
    //    ポーズ中（deltaMinutes == 0）は絶対に通さない。
    //    T4〜T9 が足す処理は必ずこの行より下に置くこと。
    //    このコメントを消すと「ポーズ中に山が育ち、建物が消え、溶岩が流れる」が起きる。
    if (deltaMinutes <= 0f) return;

    // （T4: VolcanoState.Tick がここに入る。T5〜T9 は VolcanoState の中から呼ばれる）
}
```

**この 1 行のコメントを消さないこと。** ①の `ForecastFeature` と違い、ここを early-return にしてはいけない（下のポーズガードと全要素の処理を丸ごと飛ばすことになる。②④が同じ注記を持っている）。

### 4.1 クリックから着手までは**2 往復**する（設計書に無い決定）

設計書 §4.1 は「クリック後、破壊される道路と建物の概数を出して確認を取る」とだけ書いていて、**その概数を誰がいつ数えるのかを決めていない**。ここには回避できない制約がある:

> **建物グリッドと道路グリッドは sim スレッドが所有している。** main スレッド（ツールのクリックハンドラ）から数えることはできない。

したがって⑤は次の**2 往復**を通る。**1 往復で済ませようとしてはいけない。**

```
[main] クリック → RayGeometry.IntersectTerrain で地点を取る
                → VolcanoHub.Request(Survey, point)
                → ツールを解除し、パネルを開く（「調査しています」）
        ↓
[sim ] VolcanoState.Tick が TakeRequest() で拾う
                → VolcanoSurvey.Run(...) が建物と道路セグメントを**数えるだけ**
                → Phase = AwaitingConfirmation、Footprint をスナップショットへ
        ↓
[main] パネルが確認の行を出す（下記 4.3）
                → プレイヤーが [この場所に火山を作る] を押す
                → VolcanoHub.Request(Start, point)
        ↓
[sim ] VolcanoState.Tick が拾い、Phase = Clearing へ（T5）
```

- **調査は 1 tick で終わらせる。** 上限（`MaxCellsPerPass` / `MaxBuildingsPerPass`）に当たったら `Capped = true` を立て、**概数であることを表示でさらに強く言う**。分割して数え続けない —— プレイヤーを待たせるより「概数です」と言うほうが正しい
- **確認の待ち時間に制限を置かない。** ただし `Cancel` の依頼、レベルアンロード、`VolcanoEnabled` の解除で `Idle` に戻す
- **確認の直前に設定が変わっていたら、着手せずに調査をやり直す。** `Footprint` は `Form` / `RadiusMetres` / `HeightMetres` を持っているので、`Start` を受けた時点で現在の設定と突き合わせる。違っていたら `Phase = Surveying` へ戻し、パネルは `Strings.VolcanoSettingsChanged` を出す。**古い概数で壊し始めない**
- **同時に 1 つだけ。** 既に `Idle` / `Done` / `Refused` 以外なら `Survey` も `Start` も無視して理由を診断へ出す（クラス doc に名乗る）

### 4.2 地点の取り方は③のものを使う（`TerrainManager.RayCast` に寄せない）

事実文書 §B-6 は `TerrainManager.RayCast(Segment3, out Vector3)` が public であり、③の自前マーチを置き換えられると書いている。**⑤は置き換えない。**

- ③の `RayGeometry.IntersectTerrain(origin, direction, IHeightSampler, maxDistance, out Vec3)` は**既に出荷され、実機で動いており、Core のユニットテストが掛かっている**
- `TerrainManager.RayCast` は「存在する」ことが IL で確定しているだけで、**本 MOD は一度も呼んだことがない**
- **地点の取り違えが起きる場所として、⑤の配置は本 MOD で最悪である。** 押した瞬間にプレイヤーの都市が不可逆に壊れる
- 得られるものは「自前マーチをやめられる」だけで、実測できるコストの差は無い

**この判断をツールのクラス doc に書く**（次の担当者が「バニラに public な RayCast があるのに」と言って差し替えるのを止めるため）。

`FireWhirlPlacementTool` をそのまま写す:

- `ToolBase` を継承し、**`ToolRegistration.Register<VolcanoPlacementTool>()` を `VolcanoFeature.OnLevelLoaded` で 1 回呼ぶ**。**登録しないと `SetTool<T>()` が黙って空振りする**（火災旋風 付録 A）
- `Activate()` は `ToolsModifierControl.toolController` を取り、`controller.GetComponent<VolcanoPlacementTool>()` を `controller.CurrentTool` に代入する
- `Deactivate()` は `ToolsModifierControl.SetTool<DefaultTool>()`
- `OnToolUpdate()`: `base.OnToolUpdate()` → 右クリック解除 → 左クリック以外は return → `UIView.IsInsideUI()` なら return → `Camera.main.ScreenPointToRay` → `RayGeometry.IntersectTerrain` → **`VolcanoHub.Request` を積むだけ**
- **ツールの中で `SimulationManager.instance.AddAction` を使わない。** ③は使ったが、⑤は `VolcanoHub` の依頼経路を既に持っている。経路を 2 本にすると「どちらが先に走るか」が生まれる

- **`[measured]` が付くのはこのタスクで導入する 3 行だけである**（地形高さ・建物数・道路数）。`VolcanoRows.SetMeasured` の呼び出しはこの 3 箇所しか無く、レビューはそれを数える

### 5.1 なぜ先に壊すのか（設計書 §1.2 を実装として言い直す）

`TerrainModify.UpdateAreaImplementation` は毎回 `Managers_TerrainUpdated` を呼び、そこから 7 つのマネージャが `ApplyQuad` する（§A-2）。そのうち 2 つが⑤を殺す:

```
NetSegment.TerrainUpdated  : info.m_flattenTerrain のとき Heights.PrimaryLevel(1)
                             → primaryMin = primaryMax = 道路の y
Building.TerrainUpdated    : Heights.SecondaryLevel(2)
                             → secondaryMin = secondaryMax = 建物の y（1:4 の裾つき）
反映段                     : v = Clamp(Clamp(target, secondaryMin, secondaryMax),
                                        primaryMin, primaryMax)
```

**`primaryMin` と `primaryMax` が同じ値なら、`target` に何を入れていても `v = h` に強制される。** ⑤が `RawHeights` に書いた値は完全に上書きされる。しかも**これは毎フラッシュゼロからやり直される**ので、書き続けても勝てない。

そして**ゲームは何も壊さない** —— `NetAI.AfterTerrainUpdate` は `IL_0000: ret` の 1 命令で、自動倒壊も自動デタッチも存在しない（§A-3）。

> **したがって、⑤が自分で壊さない限り、山の中に道路の平らな溝と建物のすり鉢が必ず残る。**
> **これは⑤の実装の良し悪しの問題ではなく、順序の問題である。**

**副作用として、壊せば地形固定も同時に外れる**（セルを引き戻す者が居なくなる）。設計書 §1.3 が「A. 隆起に巻き込むものを破壊する」を選んだ理由がこれである。

### 5.2 破壊は隆起の**前を走る**（ring lockstep）

設計書 §3 は「準備 → 隆起」を位相として並べ、§4.2 は「一度に全部壊さない。山が育つのと同じ速さで外側へ広げる」と書いている。この 2 つは矛盾しない —— **準備が先に始まり、隆起がその後ろを追う**。

```
clearingFront = UpliftSchedule.ClearingFrontMetres(R, progress, ModSettings.VolcanoClearingLeadMetres)
ClearedRadiusMetres = 実際に走査を終えた半径（clearingFront 以下）
activeRadius  = UpliftSchedule.ActiveRadiusMetres(R, VolcanoClearing.ClearedRadiusMetres)   ← T6
```

- **`ClearedRadiusMetres` は「壊し終えた」ではなく「走査し終えた」である。** 断られた建物（シェルター等）が残っていても走査は終わっている。**そこは⑤が壊せないと分かっている場所**なので、T6 は上げてよい（上げても押し戻されるが、それは「⑤が壊せない建物が 1 つある」という事実の可視化であって、⑤の欠陥ではない）。**この区別を doc に書く**
- **1 回の走査で `clearingFront` まで届かなかったら、`ClearedRadiusMetres` は届いた分だけ進める。** 上限に当たった状態で「全部終わった」と報告すると、T6 が壊れていない場所を上げる
- **初期値は 0。** `UpliftSchedule.ActiveRadiusMetres` が 0 を返し、隆起は 1 セルも動かない（T1 のテストが固定している）

### 6.1 1 tick でやること

```
1. activeRadius = UpliftSchedule.ActiveRadiusMetres(
                      footprint.RadiusMetres, VolcanoClearing.ClearedRadiusMetres)
   ★ 第 2 引数はこれ以外を渡してはいけない（罠 1）。activeRadius == 0 なら何もしない
2. progress = UpliftSchedule.ProgressAt(_tick, _totalTicks)
3. activeRadius の内側の全セルについて、RawHeights[z*1081+x] に
   UpliftSchedule.RawTargetAt(baseRaw[cell], profile, progress) を**絶対値で**書く
4. TileSplit のタイルを **1 枚だけ** UpdateArea する（round-robin）
5. _tick++。_tick > _totalTicks なら火口を 1 回だけ彫って Complete
```

**3 と 4 が別なのがこのタスクの肝である。**

- `RawHeights` への書き込みは**ただの配列書き込み**で、半径 2000 m でも 62501 セル、コストは無視できる。**`UpdateArea` を呼ぶまで誰も読まない**（§D-12 の「書いた人が `UpdateArea` を呼ぶまで誰も読まない」という規律）
- `UpdateArea` は**タイル 1 枚ぶんだけ**呼ぶ。**全タイルを 1 tick で呼ぶと、2 枚目以降は `merged > 10000` の判定に掛かって毎回途中フラッシュする**（§A-1 IL_00A8）。タイル数ぶんの tick をかけて一周すればよく、隆起は何百 tick も続くので**遅れは目に見えない**
- 書き込みだけ先に全域へ行き、表示が 1 枚ずつ追いつく形になる。**タイルの継ぎ目に段差は出ない** —— `TileAt` が `±2` の重なりを持って返すからである（T1 §1.2）

**元の高さ（`baseRaw`）はタスク開始時に 1 回だけ控える。** `ushort[]` を影響矩形ぶん確保する（半径 1 km で 31 KB、2 km で 123 KB、§E-13 の実費表）。**毎 tick 読み直してはいけない** —— 読み直すと⑤が前 tick に書いた値が「元の高さ」になり、**プロファイルが毎 tick 積算されて山が天井まで伸びる**。

> **`TerrainManager.BackupHeights` / `UndoBuffer` を使わない**（§E-13）。`TerrainTool` / `DistrictTool` の専有物で、`TerrainTool.OnEnable` が `RawHeights` 全体を複製し直す。**プレイヤーが整地ツールを開いた瞬間に⑤の退避が消える。** ⑤は自前の配列を持つ。
> **⑤は「火山を消す」機能を持たない**（設計書 §1.3 の「B. 不可逆でよい」）。したがって退避配列の用途は**「元の高さからの絶対目標を計算する」ことだけ**であり、セーブにも残さない。**この配列を復元機能の土台だと誤解しないこと。**

### 6.5 建物のフィードバックループ（§A-3）

### 7.1 借りるものと自作するものを、確定した事実で分ける

設計書 §4.4 は「プルームは `DisasterProperties.m_mediumExplosion` を借りられる」と書いている。**⑤はそれを主経路にしない。**

| 経路 | 事実 | ⑤の扱い |
|---|---|---|
| ⑤自前の `ParticleSystem` | ③の `FireWhirlFlameFx` が**既に出荷され実機で動いている** | **主経路。必ず出る** |
| `BuildingManager.instance.m_properties.m_fireEffect` を `RenderEffect` | **CONFIRMED**（§B-5）。`m_properties` は public、`RenderEffect` は public virtual、`SpawnArea(Vector3, Vector3, float)` の ctor あり。**DLC 不要** | 解決できたときだけ上乗せ |

**`DispatchEffect` を使わない。** `magnitude` は粒子密度であってサイズではなく（火災旋風 §4.9）、大きさは `SpawnArea` の半径で決まる。⑤は `RenderEffect` に `SpawnArea(position, direction, radius)` を渡す経路だけを使う。

### 8.1 溶岩が山を登らないことを、符号ではなく観測で保証する

### 8.2 流れ方（設計書 §4.5）

```
1. 火口から VolcanoLavaFlows 本の流れを出す
   初期方向は LavaPath.InitialDirection(seed, i, n)（等間隔＋DeterministicRandom の揺らぎ）
2. 各流れは 1 tick に数歩だけ進む（1 tick あたりの処理量を明示的に区切る）
   downhill = 勾配から作った下り方向の単位ベクトル（8.1 で符号を確定させたもの）
   LavaPath.NextPosition(head, downhill, StepMetres, out next)
3. 止まる条件（StopReason に記録して診断へ出す）
   - 勾配が MinSlope 未満（平ら or 窪み）→ 溜まる
   - TerrainManager.HasWater(head) → 水に触れた（設計書 §4.5）
   - Steps >= LavaPath.MaxSteps
   - マップの外
4. 進んだ先で着火（8.3）
```

- **1 tick あたりの歩数と流れの本数に上限を置く**（`MaxStepsPerTickPerFlow = 2`、`VolcanoLavaFlows` は最大 8）。⑤の 1 tick のコストを予測可能にする

### 8.3 着火（3 つの経路、1 つだけ DLC 分岐）

| 対象 | API | DLC |
|---|---|---|
| 地面の焦げ | `DisasterHelpers.BurnGround(new Vector2(x, z), radius, intensity)` | **不要**（§B-7b） |
| 建物 | `BuildingAI.BurnBuilding(id, ref b, group, testOnly:false)` | **不要**（§B-7a） |

**建物は走査してから `BurnBuilding` を呼ぶ。** 走査は T5 と同じ形（セル 64 / オフセット 135 / `GridChainGuard` / 次の ID を先に控える）だが、**範囲が桁違いに小さい**（`SpreadRadiusFor` は最大 60 m）。`OutwardCellOrder` を使うほどの矩形ではないので、**行優先でよい**（矩形が 3×3 セル程度なので、上限で切り捨てられる余地が無い）。**この判断を doc に書く**（②のレビュー指摘 I1 を「知らずに」破ったのではないことを示すため）。

### 9.1 `Core` に置けるのは「頂点の座標」だけ

- [ ] **Step 2: 失敗を確認し、`LavaRibbon` を実装する**

- `VertexCountFor(n)` = `n * 2`（各点の左右）／`TriangleIndexCountFor(n)` = `(n - 1) * 6`
- `Build`: `points == null || widths == null || count < 2` なら false。`count > MaxPoints` なら `MaxPoints` で切る
- 各点の進行方向は前後の点の差分（端は片側だけ）。**差分が 0 なら直前の有効な方向を引き継ぐ**（無ければ `(1, 0)`）
- 法線は進行方向を 90° 回した単位ベクトル。幅は `Max(widths[i], MinWidthMetres) * 0.5f`
- `Y` は `heightOffset` を入れるだけ（**地面の高さは Game 側が足す**）
- UV は `u ∈ {0, 1}`、`v = i / (count - 1)`

**乱数を使うなら `DeterministicRandom` だけ。`Build` の中で `new` を最小限にする**（毎フレームは呼ばれないが、伸びるたびに呼ばれる）。
