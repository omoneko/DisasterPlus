## What was implemented

- **`tools/GenerateLocaleTemplate.ps1`** — regenerates `Locales/en.txt` by
  reflecting over `src\DisasterPlus\bin\Release\DisasterPlus.dll`
  (`DisasterPlus.Game.Strings`). Preloads `UnityEngine`/`ColossalManaged`/`ICities`
  from the game's Managed dir (overridable via `CITIES_SKYLINES_MANAGED`) and
  installs an `AssemblyResolve` handler that returns `null` (never `LoadFrom`)
  for anything else, matching the working pattern in `docs/tools/ilload.ps1`.
  Verified empirically (see below) that this minimal preload is sufficient —
  no `RESOLVE MISS` occurs, because `Strings` itself has no dependency on
  `Assembly-CSharp` or the Harmony assemblies, and .NET resolves referenced
  assemblies lazily, only when a type that actually needs them is touched.

  all 18 keys and values were already correct.

## Self-review findings

1. **README compatibility section corrected against actual source, not the
   brief's draft text.** The brief's suggested README wording claimed
   "強度解放は両方が持つ機能なので、Disaster + 側は既定で無効になる" (intensity
   unlock defaults to OFF because both mods have it). This is **false** per
   `src/DisasterPlus/Game/ModSettings.cs:51`:
   `IntensityUnlock = new SavedBool("intensityUnlock", FileName, true, true);`
   — the default is `true` (enabled), unconditionally, regardless of whether
   NDR is present. There is no NDR-aware auto-disable for this setting (only
   `EarthquakeDamageOwner`'s dropdown is NDR-aware, and that setting isn't
   consumed by any code yet — it's a placeholder for the planned earthquake
   overhaul). I rewrote that paragraph to describe what the code actually
   does: `IntensityUnlock.Apply()` is idempotent (`if (slider.maxValue >=
   MaxIntensityByte) { _applied = true; return; }`), so it's safe for both
   mods to raise the cap independently — I did not carry the brief's
   inaccurate claim into the shipped README.
   I did **not** touch `src/` for this — it's a documentation-accuracy fix,
   not a code defect worth flagging as blocking.
2. **Beyond-brief addition: `LICENSE` file.** The brief's own README draft
   (and the existing Task-11 README before this task) both assert nothing
   about a license, but Step 4's target README ends with "## ライセンス /
   MIT" and no `LICENSE` file existed in the repo. Since this task is
   specifically about shipping honesty, I added a standard MIT `LICENSE` file
   (copyright holder: omoneko, matching the GitHub account referenced in your
   memory) so the README's claim has a real file behind it. This file was not
   in the brief's file list — flagging it explicitly in case you'd rather
   remove/adjust it (e.g. different copyright year format, different holder
   name).
3. **CI honesty confirmed**: the workflow's top comment states plainly that
   green means "pure logic is sound," not "the mod builds," and explains why
   (net35 + non-redistributable game DLLs can't build on a stock GitHub
   runner). Matches the brief's Global Constraint intent.
4. **Generator preload set verified empirically**, not just copied from the
   brief. I wrote a throwaway diagnostic copy of the script that logs
   `RESOLVE MISS` on any unresolved assembly, ran it against the real built
   DLL, and got zero misses — confirming the minimal `UnityEngine` /
   `ColossalManaged` / `ICities` preload (no `Assembly-CSharp`, no
   `CitiesHarmony.*`) is genuinely sufficient for loading just the `Strings`
   type, even though the DLL as a whole references `Assembly-CSharp`,
   `System.Core`, `CitiesHarmony.Harmony`, and `CitiesHarmony.API` (confirmed
   via `Assembly.GetReferencedAssemblies()` on the built DLL). This is because
   .NET resolves referenced assemblies lazily, per-type, not at
   `Assembly.LoadFrom` time.
5. **No `src/` changes.** Nothing here required a product-code change; no
