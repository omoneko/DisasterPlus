## 1. 依頼と、調査で判明したこと

### 1.1 元の依頼

> 地震について、現在は単独の断層型地震しかDLCに収録されておらず、海中で地震を発生させても
> プレート境界型地震のような津波を伴う大規模な地震は起こせません。地震の揺れによる火災や
> 建物の倒壊もおそらくランダムで、そこに長周期振動や時間帯等の因子による変化もありません。
> そして地震計があるのに地震波のグラフ等は見ることができず、都市内での震源からの距離に
> 応じた震度の分布の概念もありません。これらを実装してほしいです。

### 1.2 「倒壊はおそらくランダム」は半分間違いだった

これは本プロジェクトで**初めて、実装前に**捕まえた前提の誤りである。①では
「ハザードマップは静的リスク」という誤りに 5 タスク分の実装を積んでから気づいた。

`DisasterHelpers.DestroyBuildings` は各建物の判定を次の種で引く（事実文書 §A-3）:

```
rnd = new Randomizer(buildingID | (disasterID << 16))
```

**フレームにもステップにも依存しない。** (建物, 災害) の組に対して定数である。したがって:

- 各建物は地震ごとに**固定のしきい値を 2 個**持つ（倒壊用・出火用）
- 局所の強度係数 `fD = (destructionRadiusMax - d) / (destructionRadiusMax - destructionRadiusMin)` は
  **震央距離の線形ランプ**
- 「`fD × probability` がしきい値を超えたら壊れる」

**つまりバニラは既に決定論的な強度分布モデルである。**「ランダムに見える」のは、
建物ごとのしきい値が一様乱数だからであって、**距離減衰は最初から効いている**。

同様に `CanAffectAt` には「震央から 0.125 units/frame で外へ広がるリング」があり
（事実文書 §A-8）、これは避難判定にしか使われず**破壊にも描画にも使われていない**。

### 1.3 では本当の欠落は何か

| 依頼の要素 | バニラの実態 | 本当の欠落 |
|---|---|---|
| 震度分布 | 距離ランプが 2 系統ある（破壊・リング） | **可視化が無い**。値は既にある |
| 倒壊・火災がランダム | 決定論的な強度モデル | **見せていない**。プレイヤーが知る手段が無い |
| カメラの揺れ | `0.3/(1+dist*0.001)` の 2 正弦波 | **`m_intensity` が入っていない**（事実文書 §A-7）。強度 25.5 でも 5.5 と同じ揺れ |
| 地震計 | 半径 R に `EarthquakeCoverage` を撒くだけ | **時系列データを一切持たない**（ABSENT、§C-1）。波形は自作するしかない |
| 地震計の既存効果 | 警報 38.6 分 → 3 時間、ハザードマップに出るようになる | **UI に一切出ていない**（①と同じ構図） |
| 長周期地震動 | 0.63 / 0.17 rad/frame の 2 本のみ | **存在しない**。建物高さは揺れにも被害にも入らない |
| 時間帯 | 取得可能 | 被害に一切入らない |
| 海中震源→津波 | `TsunamiAI.FindSea` はマップ外周セルしか候補にしない | **震源から波を出すのは literally 不可能**（ABSENT、§B-3） |

**したがって②は二層になる。**

- **第 1 層「見せる」** — 既にある強度モデルを可視化する。安く、リスクが低く、依頼の大半を満たす
- **第 2 層「足す」** — 長周期地震動・時間帯・プレート境界型という**新規の物理**

この 2 層は**混ぜてはならない**。第 1 層はバニラの実測値をそのまま出すので常に正しい。
第 2 層は本 MOD が発明した数字であり、そう明示する。

## 2. 決定事項

| 論点 | 決定 | 根拠 |
|---|---|---|
| 津波の発生源 | **震源から方角だけ決める（利用者決定 A）** | `m_targetPosition` に震源を入れると `FindSea` が最も近い海側外周を選ぶ。体験は「沖の地震 → その方角から津波」。`WaterSimulation` 直叩きは `SimulateWater` 未読のため見送り（§B-3、設計への含意 1） |
| 長周期地震動 | **②に含める（利用者決定 A）** | 依頼どおり。ただし第 2 層として明示し、第 1 層と数値の出所を分ける |
| 被害判定の経路 | **`DisasterHelpers` を経由しない。** `BuildingAI.CollapseBuilding` / `BurnBuilding` を直接呼ぶ | NDR のパッチ面 2 つを完全に迂回できる（§E-2）。③で確立した方針の継続 |
| **NDR 下での第 1 層の読み取り** | **倒壊・出火の判定だけを取り下げる**（`CollapseVerdict.DamageModelReplaced`）。他の行はそのまま `[measured]` | **全体レビュー(C2) で追加。** 上の行は「**書く**側」の話で、**読む側にはまったく効かない**。NDR は `DisasterHelpers.DestroyBuildings` を Prefix が false を返す形で完全置換し、`probability == 0.02f` をバニラ地震の目印にして 0.04 を使う（§E-2 の 4 番目が「①と同じく注記を出す」と明示的に要求していたが、設計へ写されていなかった）。強度 55・しきい値 300 の建物について、この MOD は「どの距離でも倒壊しません」、NDR は「775 m まで倒れる」と言う |
| バニラ被害との関係 | **加算のみ。抑制しない（Harmony 不要）** | 既に倒壊/炎上している建物は両 API が弾く。バニラが届かない建物にだけ足す |
| ハザードマップ | ①のラッパーを流用（`SubInfoMode.EarthquakeHazard = 5`） | ゲートも塗り方も嵐と同一（§A-6） |
| 波形グラフ | **バニラの揺れ式を観測点で評価して自前のリングバッファに貯める** | `EarthquakeSensorAI` は時系列を持たない（§C-1）。式はバニラのものなので捏造ではない |
| 強度 255 対応 | **追加対策不要** | クランプはコードに存在しない（§A-5） |

## 3. 第 1 層 — 見せる

### 3.1 震度（`SeismicIntensity`）

**捏造しない。** 出す値は**バニラが実際に倒壊判定に使っている量そのもの**である。

```
R  = 2000 + m_intensity * 20            // 全体円盤の半径（§A-3）
d  = 震央からの水平距離
s  = clamp01(1 - d / R)                 // = fD（probability を掛ける前の局所強度係数）
```

`s` は「この地点でバニラが倒壊判定に使う係数」であり、**震央で 1、`R` で 0**。
これを 10 段階のバーに落とす（`Core/Earthquake/SeismicScale`）。

> **`s` は「揺れ」ではない（全体レビュー C3 で訂正）。** これは**倒壊・出火のランプ**である。
> バニラの揺れは `amp = 0.3 / (1 + dist*0.001)` で（§A-7）、**半径による打ち切りが一切無い** ——
> `R` の外でもカメラは揺れ、波形も非ゼロである。当初の設計は `s` の行を
> 「カーソル地点の揺れ」と名付け、`R` の外を「揺れの範囲外」と表示していたが、それは
> 同じフレームで `CameraShakeBooster` と `SeismographRecorder` が出している値と
> 真っ向から矛盾する主張だった。**行は「破壊係数」と名乗り、揺れの振幅は別行で出す**
> （`ShakeWaveform.PeakAmplitudeAt`、こちらも第 1 層）。

> **気象庁震度階級を名乗らない。** 本 MOD の `s` は加速度でも計測震度でもなく、
> ゲームの倒壊係数である。実在の尺度の名前を借りると、実在の意味があると誤解させる。
> **段階ラベル（弱い/中程度/強い/非常に強い）も第 1 層では出さない**（同じく C3）。
> あれは本 MOD が付けた名前であって、`[measured]` の下に置くとゲームがその判断を
> していることになる。第 1 層は数値とバーだけにし、名前は第 2 層が名乗る。

**断層の 4 円盤は別扱い。** あれは `probability = 1` で `w` 以内をほぼ確実に破壊する（§A-3）。
全体円盤の `s` とは意味が違うので、`s` に混ぜず「断層帯」として別に示す。

**帯の広がりは `1.5w`（全体レビュー C1 で訂正。当初は `2w` としていた）。**
呼び出しの実引数は `preRadius: w` で、`DisasterHelpers.DestroyBuildings` は
`if (dist >= preRadius) continue;` を種の生成よりランプの計算より**前**に置いている
（IL_0130 の `bge.un`）。`destructionRadiusMax = 2w` が入るのは `fD` の分子だけで、
`dist < w` では `fD > 1`、そこに `probability = 1` が掛かるので比較は無条件に真になる。
**円盤 1 個の到達距離は `w` ちょうど**である。これに蛇行（円盤中心を直交方向へ最大 `0.5w`
ずらす、IL_0201–023E）を足して `1.5w`。沿走方向も同様に、中心の上限 `0.4L` に `w` が足される
（当初は `|t| > 0.4` を無条件に外側としており、両端をちょうど `w` ぶん取りこぼしていた）。

### 3.2 建物ごとの余裕度（本機能の目玉）

`Randomizer(buildingID | (disasterID << 16))` を**同じ種で再構成できる**（§A-3）。
つまり②は、バニラが引くのと**同一のしきい値**を先読みできる。

```
rnd  = new Randomizer(buildingID | (disasterID << 16))
tD   = rnd.Int32(10000)                 // 倒壊しきい値（1 回目の引き）
tB   = rnd.Int32(10000)                 // 出火しきい値（2 回目の引き）
壊れる ⇔ tD < fD * probability * 10000
```

→ 「この建物は震央からの距離がここまで来たら倒れる」が**予言ではなく事実として言える**。
これを情報ビューで見せるのが第 1 層の中核である。

> **`tB`（2 回目の引き）も必ず表示する（全体レビュー M1 で追加）。** 依頼文は
> 「揺れによる火災**や**建物の倒壊」と明示的に火災を挙げている。全体円盤では
> `burnRadiusMin = 0, burnRadiusMax = R` なので `fB = fD = 1 - d/R` となり、
> **倒壊とまったく同じランプ・同じ probability・違うのはしきい値だけ**である。
> ただし IL は `else if (hitB && ...)` なので**倒壊が優先する**（倒壊した建物は
> `burnAmount = Round(fB*255)` を受け取る）。その順序も併記すること。

> **NDR が入っている環境では、この 2 つの結論を出さない**（全体レビュー C2、§2 の表）。
> しきい値も距離も出せるが、**判定だけは出せない**——`FaultBand.Known == false` の
> ときとまったく同じ扱いである。

> **`Randomizer` は `Core/` に持ち込めない**（ColossalFramework の型）。
> `Core/Earthquake/CollapseThreshold` は「しきい値 2 個と `fD` と `probability` を受け取って
> 壊れるかを返す」純関数に留め、種の再構成は `Game/` 側で行う。
> **`Randomizer.Int32(int)` の実際のビット列を IL で確認してから写すこと**（付録参照）。

### 3.3 カメラの揺れに強度と距離を入れる

バニラの `RenderInstance` は振幅に `m_intensity` を入れていない（§A-7）。
`CameraController.m_cameraShake`（public）に**足す**ことで補正する。抑制はしない。

```
追加分 = バニラと同じ位相の波 × (m_intensity / 55 - 1) × 距離減衰
```

- `m_intensity = 55`（バニラ既定）で追加分 0 = **バニラと完全に同じ挙動**
- 55 未満では負、つまり弱い地震はより弱く揺れる
- レンダリング側が毎フレーム消費するので毎フレーム足す（`ThreadingExtensionBase.OnUpdate`、メインスレッド）
- `DisasterManager.m_disableCameraShake` が true のときは**足さない**（プレイヤーの意思を尊重）
- 上限を設ける。強度 255 で画面が使い物にならなくなるのは不具合であって迫力ではない

### 3.4 地震計の既存効果を見せる

**波形より先にこれを出す。**「地震計を建てると何が変わるか」がゲーム内のどこにも書かれていない。

| 効果 | 出典 |
|---|---|
| 警報リードタイムが 1755 → 最大 8192 フレーム（38.6 分 → **ちょうど 3.0 時間**）に伸びる | §A-2 |
| `located = true` になり、**ハザードマップに地震が塗られるようになる** | §A-2 / §A-6 |
| カバレッジは `Min(coverage, 100)` で頭打ち | §A-2 |

現在のカバレッジは `ImmaterialResourceManager.CheckLocalResource(Resource 22, pos, out int)` で読める。
①で「なぜハザードマップが空なのか」を説明したのと**同じ構図**であり、同じ文体で書く。

### 3.5 波形グラフ

観測点（各地震計の位置）でバニラの揺れ式を評価する（§A-7）:

```
e   = currentFrame - m_activationFrame + 128        // e <= 0 または e >= m_activeDuration なら 0
amp = 0.3 / (1 + dist * 0.001)                       // dist は観測点と震源の距離
amp *= 0.5 - 0.5 * cos(t * 0.02454369)               // 256 フレーム周期の包絡線
y    = (sin(t * 0.63) + sin(t * 0.17)) * amp
```

> **バニラ式は `camera.transform.InverseTransformPoint` を使う**（§A-7 IL_003F）ため、
> 厳密には「カメラからの距離」である。観測点版はそこを**震源からの距離**に置き換える。
> これは同じ式の別評価であって近似ではない。**その差を設計書と UI の両方に書く。**
> 第 3.3 節の追加シェイクとは別の量なので、波形に追加分を混ぜない。

> **サンプルは 1 sim tick に 1 点ではなく、飛んだフレームを全部埋める**
> （全体レビュー I5 で訂正）。`m_currentFrameIndex` は 1 tick で `FinalSimulationSpeed`
> （速度 1/2/3 で 1/3/9）進むのに、主成分は 0.63 rad/frame ＝ 周期 ≒10 フレームである。
> 9 フレームおきに 1 点だけ取ると**周期 ≒92 フレームの偽の波**に折り返し、その見た目は
> **長周期地震動そのもの** —— §A-7 が「バニラに長周期成分は無い」と確定させ、
> 本設計が第 2 層に置いた現象を、第 1 層のグラフが描いてしまう。上の式は `e` の
> 閉じた形なので、tick 内の各フレームで評価するのは 1 回評価するのと同じだけ実測である。
> （`WaveformPlot` が時間軸をフレームで割っているのは、この問題の**もう半分**にすぎない。）

> **最大振幅のバーの満目盛りは `2 × 0.3 = 0.60`**（同じく I4）。局所係数 `s` の
> 0-1 の目盛りを流用すると、最大でも 0.6 にしかならない量が常に 1〜2 マスしか
> 埋まらず、すぐ上の `s` のバーと見分けが付かなくなる。満目盛りは数値でも併記する。

リングバッファは sim スレッドで書き、`ForecastHub` と同じ snapshot-then-render でメインへ渡す。
セーブには**残さない**（地震終了で捨てる。セーブ形式を増やす価値が無い）。

## 4. 第 2 層 — 足す（本 MOD が発明した物理）

**第 1 層と視覚的に区別する。** 数値の横に出所を書く。

### 4.1 プレート境界型地震

海中に震源を置いたとき、遅延して津波を起こす。

```
1. 震源が水中か: TerrainManager.instance.HasWater(VectorUtils.XZ(pos))   ※ 存在と public 性を IL で確認すること
2. 水中なら、地震の Active 開始から N フレーム後に TsunamiAI を起こす
3. m_targetPosition に震源を入れる → FindSea が震源に最も近い海側外周区間を選ぶ（§B-3）
4. m_intensity は地震の強度から導出（津波の波高は m_height * 64 * i / 55、§A-5）
```

**必ず守ること:**
- `CreateDisaster` の**戻り値を見る**。false のとき `disasterIndex = 0` になり、
  無視すると他人の災害スロットを書き潰す（§E-1）
- `m_flags |= SelfTrigger (64)` を立てる。**立てないと `StartDisaster` が即 return し、
  災害が Emerging のまま永久に固まる**（§A-1、地震・津波の両方）
- `FindDisasterInfo<TsunamiAI>()` が null なら DLC が無い。**何もせず理由を診断に出す**（§B-5）
- `FindSea` は海側区間が 10 セル未満だと false を返し、**津波は起きない**（§B-3）。
  内陸マップでは正常に何も起きない。これを失敗として扱わない

> **「震源から波が広がる」ではない。** 波は必ずマップ外周から来る。
> UI の文言を「震源に最も近い海から津波が到達します」にし、実装できていないことを
> できているかのように書かない。

### 4.2 長周期地震動

**新規の物理である。** バニラには存在しない（§A-7、建物高さは揺れにも被害にも入らない）。

```
長周期成分 = 低周波の正弦波（バニラの 0.63 / 0.17 より十分低い周波数）
建物の応答 = 建物高さから決まる固有周期と、長周期成分の周期の近さ
追加被害   = 応答 × 震央距離の緩やかな減衰（短周期より遠くまで届く）
```

- 建物高さは `Building.Info.m_generatedInfo` 系から取る。**具体的なフィールド名を IL で確定してから書く**
- 対象は**バニラが壊さなかった建物だけ**。既に倒壊/炎上しているものは `CollapseBuilding` /
  `BurnBuilding` が弾くので、二重被害にはならない
- **既定で ON にしない。** 新規の物理を既定で入れると、プレイヤーはバニラの挙動が
  変わった理由を知る手段が無い。設定で明示的に有効化させる
- 走査はバニラの `DestroyBuildings` と同じグリッド走査（セル 64、オフセット 135、`[0,269]` クランプ）。
  **sim スレッド専用**

### 4.3 時間帯係数

```
sim スレッドでの時刻 = SimulationManager.instance.m_dayTimeFrame * SimulationManager.DAYTIME_FRAME_TO_HOUR
```

**`m_currentDayTimeHour` を sim スレッドから読まない。** メインスレッドが
`m_referenceFrameIndex`（描画補間側）から書くフィールドであり、スレッド跨ぎかつ値の出所が違う（§F-1）。

> **罠（§F-1）。** 日夜サイクル OFF かつゲームモードのとき、`m_dayTimeOffsetFrames` が毎 sim フレーム
> 再設定され、**時刻は永久に 12.0 に固定される**。時間帯係数はその設定では黙って定数になる。
> → `Assumptions` に「日夜サイクルが無効なので時間帯差は出ません」を出す。**黙って無効にしない。**

係数は控えめにする。「夜の方が被害が大きい」はバニラのどこにも根拠が無い。

## 5. 構成

```
src/DisasterPlus/
  Core/Earthquake/                 エンジン非依存・全部ユニットテスト対象
    SeismicIntensity.cs              距離と R から s を出す純関数
```

### A-1. `Randomizer` — CONFIRMED（本書執筆時に実測）

`ColossalFramework.Math.Randomizer`（**`ColossalManaged.dll`**、`Assembly-CSharp` ではない）。
フィールドは `UInt64 seed` の 1 個だけ。古典的な LCG（Knuth MMIX 定数）である。

```
.ctor(Int32 v)            // IL_0000-001C
    seed = 6364136223846793005 * (long)v + 1442695040888963407

Int32(UInt32 max)         // IL_0000-0030。DestroyBuildings が呼ぶのはこの overload
    戻り値 = (int)(((seed >> 32) * (ulong)max) >> 32)      // shr.un ×2、conv.u8、conv.i4
    seed  = 6364136223846793005 * seed + 1442695040888963407   // 戻り値を作った「後」に進める
```

overload は `Int32(UInt32)` / `Int32(Int32,Int32)` / `UInt32(UInt32)` / `UInt32(UInt32,UInt32)` / `Bits32(Int32)`。
`Int32(int)` は**存在しない**（`DestroyBuildings` の `rnd.Int32(10000)` は `UInt32` 版）。

**Core 側で完全に再現できる。** `ulong` の算術だけで書け、`UnityEngine` にも
ColossalFramework にも依存しない。実装上の注意:

- **`unchecked` を明示する。** 乗算は必ず 64 bit で溢れる。
  `.NET 3.5` ビルドと `net8.0` テストビルドの両方で同じ結果になることをテストで固定する
- 戻り値は**種を進める前**に計算される。順序を入れ替えると全部ずれる
- ctor の乗算は `long`、以降は `ulong`。`(long)v` の符号拡張が効くので
  `buildingID | (disasterID << 16)` が負になる場合（`disasterID >= 0x8000`）も再現すること。
  災害 ID は 1〜255 なので実際には起きないが、テストで固定しておく

これで第 3.2 節の「建物ごとの余裕度」は**予言ではなく事実**として出せる。
